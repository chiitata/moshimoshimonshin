## 初回確認

オーナーが月額予算・通貨・通知先・日次確認担当・代替担当・変更承認者を確定する。
金額や宛先を推測しない。既存設定を確認してから変更し、重複予算を作らない。
予算読み取り権限がない場合は、権限を持つ請求担当へ以下の確認を依頼する。
権限不足を「予算なし」「支出ゼロ」と記録しない。

1. Cloud Billingで対象プロジェクトの請求先を確認する。請求先や担当者の詳細は非公開台帳へ記録する。
2. 予算のproject filter、期間、金額、通貨、クレジットの扱いを記録する。
   対象外プロジェクトを含む予算だけでは本Issueの受入としない。
3. 実費50%・80%・100%の通知条件と実際の受信担当を照合する。
   予測額の通知を使う場合は実費通知と区別する。
4. 通知先の有効性と担当者の受領確認を記録する。実送信を伴う確認は担当者と調整する。
   設定画面の存在だけを配送確認としない。

通知のみの予算は支出を止めない。対応サービス限定の支出上限機能があっても、
このシステム全体の停止保証とは扱わない。[公式の予算説明][budgets]

## API上限の台帳

GCP Consoleの対象projectを明示し、Quotas & System LimitsでAPIごとに確認する。
設定変更の前にquotaの単位・期間・適用範囲を確認する。[公式のquota管理][quotas]
本番上限を試すための負荷送信や、検証目的の上限引下げは行わない。

| 対象 | 記録する項目 | リポジトリの照合先 |
|---|---|---|
| Cloud Run API/worker | min/max instances、CPU/メモリ、concurrency、timeoutと実revision | `infra/terraform/cloud_run.tf` |
| Places | 有効なAPI/SKU、quota名・単位・上限・適用範囲、現在使用量 | コスト試算表 §4 |
| LLM | 承認済みprovider/model/region、リクエスト・token上限、再試行上限 | コスト試算表 §3・§10.2 |
| OCR | 採用processor、ページ/ファイル上限、再試行上限 | コスト試算表 §5 |

各行に「確認日時UTC・確認担当・現行値・承認済み目標・差分・変更記録」を付ける。
未採用サービスは採用状況の根拠を添えて対象外とし、未確認をゼロ扱いしない。
GCP quotaとアプリ内のユーザー単位制限は別々に確認する。
quotaを引き上げる場合は費用影響とロールバック値を承認者へ提示する。

## 定期レポート

日次確認担当は前日分と当月累計を確認し、月次担当は請求月の締め後に試算を更新する。
Billing Reportsまたは既存の承認済みBilling exportを用い、
project・期間・通貨・サービス/SKUの集計条件を毎回揃える。
exportが未設定ならその旨を記録し、Reportsで確認できる範囲と分ける。
新しいexport先の作成はこの手順の読取作業に含めない。

標準exportには費用・クレジット・通貨・請求月等が含まれる。
データ到着には遅延があり、利用期間と請求月を同一視しない。[標準exportの仕様][export]

非公開台帳には次の1行をサービス/SKUごとに記録する。

| 確認UTC | 利用期間/請求月 | 通貨 | サービス/SKU | 費用 | 符号付きcredits合計 | 差引費用 | 前日/過去7日比較 | 試算との差・対応 |
|---|---|---|---|---|---|---|---|---|
| 未確認 | 未確認 | 未確認 | 未確認 | 未確認 | 未確認 | 未確認 | 未確認 | 未確認 |

差引費用は費用に符号付きcreditsを加算する。通貨を混ぜて合算しない。
円換算が必要ならレート・基準日と換算前金額を別記し、請求通貨の値を残す。
前日比・7日比較は同じ集計条件とデータ到着状況で行い、ゼロ除算や欠測は比率なしとする。
患者ID、自由記述、画像パス、token、API key、請求先ID、通知先を公開Issueへ転記しない。

## 乖離・通知への対応

- 50%: 当月累計・データ遅延・対象範囲を確認し、増加したSKUと理由を調べる。
- 80%: オーナーへ残予算と利用傾向を報告し、既存の承認済み制限と変更候補を提示する。
- 100%: 継続/抑制の判断をオーナーへ求める。通知だけで停止済みと報告しない。

これは運用の確認段階であり、自動停止の実装ではない。
APIの停止やquota削減は利用者への影響と戻し方を確認してから承認された範囲で行う。
変更後は設定値とエラー率を確認し、試算表の入力値・未計上費目・料金改定の差を記録する。
未実装のfeature flagを使用可能な停止手段として扱わない。
