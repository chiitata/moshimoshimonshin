## 1. 共通UI仕様

### 1.1 画面デザインシステム

- Material 3 Expressiveの思想（明確な階層、まとまり、押しやすさ）を採用。ただしFlutterのMaterial 3 API/デザイン部品がすべてExpressiveに対応するとは限らないため、パーツ単位で検証 [S01]。
- 本文サイズ初期20sp、強調22～26sp、見出し28～32sp。OSテキスト倍率を尊重し、固定高さレイアウトを避ける。
- タップ領域目標48×48dp以上、主要な選択カードは高さ72～96dp。大きな文字でも要素が重ならない。
- 1画面1質問。最大3件の主要選択肢、「わからない」「答えたくない」「戻る」「中断」を別固定アクションにする。
- 視認性：WCAG 2.2 AA相当を品質目標。意味を色だけに依存せず、コントラスト・フォーカスリング・読み上げを提供。
- ボタン文言は「次へ」「この病院に送る」等の動作が分かる動詞。アイコン単独の重要ボタンを避ける。
- 操作フィードバック：ローディングは読み上げ可能な進捗ラベル、長時間待ちで「時間がかかっています。続ける/後で再開」を案内。
- 「○○病が疑われる」「絶対に大丈夫」「受診不要」といった診断と誤認される文言を生成しない。
- Web/PWAではページ戻り操作による下書き欠損を防止。iOS/Androidでは画面を離れてもローカルにPHIを平文で長期保存しない。

### 1.2 共通状態

| 状態 | 表示 | 挙動 |
|---|---|---|
| `loading` | 読み上げ対象の処理中 | 二重送信禁止。経過後は再試行/固定質問 |
| `empty` | 内容がありません | 次の取るべき操作を1つ表示 |
| `partial` | 途中まで入力済み | 再開・編集可能 |
| `validation_error` | 入力箇所直下の平易な説明 | 焦点を不備項目へ移動 |
| `network_error` | 接続できませんでした | 保存状態を維持しリトライ |
| `auth_expired` | 再ログインが必要 | 下書きを安全に再関連付け |
| `permission_denied` | 権限がありません | 本文や機微な存在確認情報を漏らさない |
| `rate_limited` | 少し時間を置いて再試行 | Retry-Afterを尊重 |
| `service_unavailable` | この操作は一時的に使えません | 固定問診/オフライン案内 |

## 3. 画面の個別動作仕様

### 3.1 P-004 メール新規登録時の同意 / P-002 Google・Passkey初回追加情報・同意

- **メール新規登録（P-004）**：メール・パスワードとともに、利用規約、プライバシーの確認、医療情報取得目的を表示し、**必須項目を個別の未チェックcheckbox**にする。利用者が同意した場合だけ `POST /auth/register` を送信する。Cloud Runも同意と文書版を検証し、**拒否時はAdmin SDKのユーザー作成処理に入らない**。成功後はFirebase Client SDKでサインインし、P-006へ進む。
- **Google・Passkey初回利用（P-002）**：認証成功・ID token取得後にP-002を表示。利用規約・プライバシー説明・医療情報取得の必須チェックを個別に確認し、`POST /onboarding/consents` の確定応答までP-006へ進めない。未同意なら問診・プロフィールPHI保存不可。OAuth認証で先に作られたAuth UIDは、アプリ利用権限とは区別する。
- **既存利用者の規約改定**：`GET /me` で再同意要否を判定しP-002へ。更新済みの同意記録が書き込まれるまではPHI系APIを停止する。
- どの経路も最新版リンクを表示し、必須・任意の解析同意・医療機関ごとの第三者提供同意を分離する。患者の「同意しない」選択は尊重し、Auth生成・業務API利用を拒否するが、読むだけの公開文書は閲覧可能。
- 記録は `documentType/consentType`、`documentVersion`、正式版 `documentHash`、`occurredAt`（サーバ時刻）、`method=explicit_checkbox`、`locale`、`registrationSource`。クライアントの `consentedAt` や自由指定の文書ハッシュを正本にしない。デバイス/IPは必要性と保存期間を評価する。

### 3.3 P-010 症状入力

- プレースホルダー例：「例：2週間ほど、夕方になると体がだるい。日によって違います」。患者からの原文として保存。
- 必須：1文字以上/暫定1000文字以内。HTML/スクリプトは実行せず安全に表示。送信時レート制御。
- 入力内容をGA4/Crashlytics/アプリログに書かない。
- `CreateIntake` 成功時に intakeId と revision を取得し、再送・重複作成を防止。

### 3.4 P-011 人体図

- 2D正面・背面、必要なら上下半身切替。人体図は医学画像による診断ではなく体の位置を指し示す操作補助。
- 身体部位キー例：`head`, `neck`, `chest`, `abdomen`, `back`, `left_arm`, `right_arm`, `left_knee`, `right_knee`, `left_leg`, `right_leg`, `whole_body`, `unsure`。
- ピンは重なりを回避。拡大でき、キーボード/スクリーンリーダー利用者には同等のテキスト選択リストを提供。
- 痛みのない症状には `whole_body`, `unsure`, `not_applicable` が必要。
- 両膝など複数部位可。左右は画面上の画像の左右ではなく**患者本人の左右**と明記。
- 任意選択であり、身体図をスキップしても問診を進められる。

### 3.5 P-013 AI質問

- 上段：`質問 4 / 最大12問（目安）`。残数は確定でない場合「あと数問」と表現。
- 質問文：40～80字以内を目安。医療用語を避け、難しい語には注釈。
- 選択肢：モデル生成は原則3件。固定操作「わからない」「答えたくない」「前に戻る」は必ず追加。
- 回答選択後に保存し次質問へ。保存中は連打不可。バック操作によって後続の依存質問は破棄/再生成。
- 12問以内（暫定）を上限に要約へ進む。重大な未回答項目は未回答のまま表示。
- モデルエラー：自動で2回以内再試行、失敗時「用意された質問に切り替えました」と案内。
- 不安が高まる可能性のある文言や疾病名の断定を出した場合は表示前に検査し、患者には固定質問を提示。
- 会話の全履歴を毎回送信せず必要な状態のみ送信。プライバシーとトークン費用を抑える。

### 3.6 P-014 レビュー

```
問診票の確認（例：合成データ）
主な症状：夕方になると体がだるい
いつから：2週間ほど前
頻度：日によって異なる
痛む場所：特に指定なし
持病：高血圧、変形性膝関節症（本人登録）
飲んでいる薬：1件（本人確認済）
分からなかったこと：疲労感の強さ
```

- 未回答の項目は「なし」に変換せず「未確認/未回答」とする。
- 症状の原因・医師向け診断を付け足さない。
- 誤りがある箇所から編集できる。確定するまでは送信不可。
- 患者が選択した薬だけを添付。画像自体の送信は別の明示操作とする。

### 3.7 P-030〜033 病院と送信

- 検索：アプリは位置情報を取得する前にOSの権限ダイアログを表示。拒否しても手入力継続。
- Placesから得られる「hospital」「doctor」は施設の医療法上の認可や診療可能性を保証しない。必要に応じて別の公的施設データ等で確認する。
- 施設には「このアプリで問診を受け取れる」のラベルと、運営確認日を表示。
- 送信画面に患者自身が決めた宛先、問診票の内容、画像を含むか、同意チェック欄を表示。
- `POST /deliveries` の応答が202なら「送信を受け付けました」、受信箱反映後に「届きました」と分ける。
- 問診票の送信は診療予約・医師の確認・受診受入れを意味しないことを必ず表示。

### 3.8 医療機関管理画面

- 1ページ20件。`receivedAt`降順、サーバcursorページング。自由検索は自院内だけ。
- 初期一覧に原文症状の全件表示をしない。患者表示名、受信時刻、状態、問診票ID程度に抑える。
- 詳細を開くたびに「職員、施設、対象票、時刻、用途」を監査記録。印刷・エクスポートは権限分離し、不可とするか別途審査。
- 施設管理者は自院の招待・停止が可能。運営が検証した事業者の真正性情報を自分で上書きできない。
- 画面タイムアウト・ロック・MFA再認証。共有パソコンを想定した自動サインアウト。

## 4. API共通規約

### 4.1 バージョンと形式

- REST/JSON、URI `v1`、UTF-8。ISO8601のAPI日付時刻はUTC `Z` 形式。UI表示はAsia/Tokyoに変換。
- `snake_case` か `camelCase` は全体で統一し、以下は `camelCase`。
- 共通ヘッダー：`X-Firebase-AppCheck`、`X-Request-Id`。認証済みAPIは `Authorization: Bearer <Firebase ID token>` が必須。**認証前の `POST /auth/register` のみAuthorization不要**（App Check・レート制限は必須）。副作用POSTには正規名 **`Idempotency-Key`** を使う（`X-Idempotency-Key` は禁止）。
- リソースのPUT/PATCHには `If-Match` と `ETag` または `revision` 検証で競合を防ぐ。
- 患者APIのユーザーIDは原則URLに明示せず、検証済みFirebase `uid`から解決。
- 病院APIは施設スコープがURLに出ても、それを権限証明として扱わない。
- 安全のため正常/異常レスポンスに医療情報を不用意にエコーしない。

### 4.2 標準エラー

```json
{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "入力内容を確認してください。",
    "fieldErrors": [{"field": "birthDate", "message": "正しい日付を選んでください。"}],
    "requestId": "req_01J...",
    "retryable": false
  }
}
```

| HTTP | code | 発生条件 | UI |
|---:|---|---|---|
| 400 | VALIDATION_FAILED | 形式/長さ/Enum不正、必須checkbox=false | 入力箇所へ案内 |
| 409 | REGISTRATION_CONFLICT | 同じ登録キーで異なるペイロード・既存メール競合等 | 既存アカウントへの無断紐付けは行わない |
| 401 | UNAUTHENTICATED | Token不正/期限 | 再ログイン |
| 403 | FORBIDDEN | 別テナント/不同意/退会中 | 汎用権限エラー |
| 404 | NOT_FOUND | 存在しない/閲覧権限なし | 資源不明を統一 |
| 409 | REVISION_CONFLICT | 他端末編集 | 再読み込み・変更確認 |
| 409 | ALREADY_DELIVERED | 同一配送命令の競合 | 同一配達結果を表示 |
| 412 | PRECONDITION_FAILED | 必要な同意/確定/施設審査が不足 | 条件を案内 |
| 413 | FILE_TOO_LARGE | アップロード上限超過 | 画像縮小案内 |
| 422 | MODEL_SCHEMA_REJECTED | AI応答の検証失敗 | 固定質問へ切替 |
| 429 | RATE_LIMITED | 呼出超過 | Retry-Afterを表示 |
| 503 | UPSTREAM_UNAVAILABLE | OCR/LLM/Places故障 | 再試行か代替手段 |

### 5.1 POST /auth/register と POST /onboarding/consents

**メール新規登録（ID tokenはまだないためAuthorizationを付けない）**：

```http
POST /v1/auth/register
X-Firebase-AppCheck: <APP_CHECK_TOKEN>
X-Request-Id: req_example
Idempotency-Key: 2a6e8f11-6b8c-42e3-965b-d8ccac641acd
Content-Type: application/json

{
  "email": "user@example.com",
  "password": "<USER_ENTERED_PASSWORD>",
  "consents": {
    "terms_of_service": {"accepted": true, "documentVersion": "terms-v1"},
    "privacy_policy_ack": {"accepted": true, "documentVersion": "privacy-v1"},
    "health_data_collection": {"accepted": true, "documentVersion": "health-v1"}
  },
  "locale": "ja-JP"
}
```

上記文書版は**構造例**（公開API `/public/legal-documents` で取得する正式版のみ受理）。`privacy_policy_ack` は内容確認の証跡であり、第三者提供同意とは別。必須種別は法務承認済み設定をサーバが決定し、任意の解析同意は省略または別同意として扱う。**チェックが偽・欠落・旧版ならAuth作成前に400/412で拒否**する。

```http
HTTP/1.1 201 Created
Content-Type: application/json

{"registrationStatus":"created","nextAction":"sign_in","onboardingState":"profile_pending"}
```

- Cloud Runの内部順序：App Check/不正登録制御 → 必須同意/版検証 → 冪等操作予約（UID確定） → Admin SDK `createUser(disabled=true)` → Firestore transaction（account, legalConsents, operation） → Auth有効化 → `201`。
- `401` ID token前提の通常middlewareをこのルートへ適用しない。Firebase Auth/Firestore横断ACIDは不可能なので、障害発生時は同じ `Idempotency-Key` で安全に再試行、未完成アカウントは利用不可のまま修復・期限付きクリーンアップする。
- Firebase Admin SDKに送信されたパスワードはサーバからログ/Firestore/キューへ複製しない。HTTPSのみ。登録成功後、クライアントが `signInWithEmailAndPassword` でログインし、メール認証を案内する。APIはpassword、ID token、署名済みセッショントークンを応答しない。

**Google/Passkey初回・再同意（ID tokenあり）**：

```http
POST /v1/onboarding/consents
Authorization: Bearer <FIREBASE_ID_TOKEN>
X-Firebase-AppCheck: <APP_CHECK_TOKEN>
Idempotency-Key: a3e6bb7c-a40b-40cf-9f74-3bbb6674c85f
Content-Type: application/json

{
  "consents": {
    "terms_of_service": {"accepted": true, "documentVersion": "terms-v1"},
    "privacy_policy_ack": {"accepted": true, "documentVersion": "privacy-v1"},
    "health_data_collection": {"accepted": true, "documentVersion": "health-v1"}
  },
  "locale": "ja-JP"
}
```

- Firebase ID tokenから得たUID以外への記録を禁止。承認済み版の `legalConsents` と `accounts/{uid}.onboardingState=profile_pending` をFirestore transactionで確定。応答 `200 {"onboardingState":"profile_pending"}`。
- このAPIと公開文書取得・`GET /me` 等の限定例外以外は `legal_pending` からアクセス不可。初回認証が失敗/キャンセルされた場合はP-002へ移行せず、医療情報を保存しない。
- `POST /consents` は **廃止**。初回同意はメールなら `POST /auth/register`、Google/Passkeyと改定時再同意は `POST /onboarding/consents`。同意履歴参照 `GET /consents` は維持する。

## 6. 業務ロジックとイベント

### 6.1 問診プロセス

```text
createIntake
  assert accountStatus == ACTIVE and requiredConsentsCurrent
  create intake(status=DRAFT, revision=1)

submitInitialSymptom
  validate size/type; run fixed safety policy
  save raw answer + body locations

nextQuestion
  if aiApproved and modelAvailable and underBudget:
    request model with minimal structured context
    parse strict JSON; validate question & choices
    if invalid: use deterministic next question
  else:
    use deterministic next question
  persist question snapshot before returning

answerQuestion
  validate same question revision
  save patient answer; invalidate dependent branches
  increment intake revision

finalize
  require patient review
  create immutable questionnaire version/hash
  mark intake=FINALIZED
```

### 6.2 OCR処理と人手確認

- OCR Job：`queued → preprocessing → processing → review_required → confirmed`。失敗時 `failed_retryable / failed_terminal`。
- `review_required` の候補は原文・認識信頼度・抽出モデル・元画像参照を保持。
- 「名前が似ている別薬」「容量・単位を取り違えた薬」は重大な誤りにつながるため、薬剤名も規格も必ず本人確認。
- 患者が確認できない場合は「未確認の薬」として保存し、服用している薬と断定して表示しない。
- 薬剤の一般説明は、出所が明確な監修済みデータのみ。LLMに自由な効能説明・服薬指示を生成させない。

### 6.3 医療機関への配送

- `created`: Delivery作成のトランザクション完了。
- `delivered`: 自院受信箱から取得可能。
- `acknowledged`: 医療機関担当者が操作。
- `failed`: 配送不成立。患者には「まだ届いていません」と明記。
- `revoked`: 未閲覧/未処理の場合の取下げ可否を別途規定。受信済みデータの遡及削除を保証しない。

### 6.4 イベント命名

| イベント | 目的 | 送ってよい属性 | 送信禁止属性 |
|---|---|---|---|
| `onboarding_completed` | 完了率 | appVersion, platform | 氏名、電話、住所、病歴 |
| `intake_started` | 入口計測 | uiVariant | 自由記述本文 |
| `question_answered` | UX計測 | questionCount, latencyBucket | 選択肢の内容・症状名 |
| `summary_reviewed` | 修正率 | didEdit（boolean） | 具体的な修正内容 |
| `medication_ocr_completed` | OCR性能 | resultCount, durationBucket | 薬剤名/画像/原文 |
| `facility_search_used` | 検索UX | manualLocationUsed（boolean） | 詳細な緯度経度 |
| `delivery_completed` | 送信率 | success（boolean） | 施設名・患者ID・病歴 |

GA4へのデータ送信は関係するデータ利用条件・同意とSDK設定を確認してから。広告識別やプロファイリングを目的とした利用は初期採用しない。

## 10. 主要なE2Eテスト

### E2E-001 正常な患者問診・送信

1. Googleでサインイン。2. 必須同意。3. プロフィール完了。4. 「2週間夕方だるい」を入力。5. 全身/不明を選択。6. 3択に回答。7. 要約レビュー。8. 参加施設検索。9. 送信前プレビュー/同意。10. 送信受付。11. 病院側で閲覧。**期待結果**：配送した版と病院受信版のハッシュが一致し、audit trailが残る。

### E2E-001B メール新規登録の同意ゲート

1. P-001→P-003→P-004。2. 必須同意が全て未選択なら送信不可。3. 1項目を未同意にしてAPIを直接叩いてもAuth UIDは作成されない。4. 全項目に同意して `POST /auth/register` が成功。5. Firebase Client SDKでサインイン。6. P-006プロフィール登録。7. 必要なメール検証/プロフィール処理を経てP-007。**期待結果**：Firestore同意記録の版/ハッシュ/時刻とAuth UIDが対応し、途中失敗でも未同意ユーザーは利用不可。

### E2E-001C Google/Passkey初回登録の同意ゲート

1. P-003でGoogle（Passkeyは検証済み構成に限る）認証。2. `GET /me` が `legal_pending` ならP-002。3. `POST /onboarding/consents` 失敗時は再試行可能だがP-006/問診へ進めない。4. 同意成功後P-006。**期待結果**：既存利用者や改定時再同意にも循環依存なし。

### E2E-002 ネットワーク断と再開

質問回答の保存後、次質問取得時に通信を遮断。接続回復・再ログイン後、同じ回答が重複せず表示。LLMが復旧しなければ固定質問で進行。

### E2E-003 薬剤誤抽出

処方箋の薬剤が誤認識される。ユーザーが候補を修正し「服薬状況は不明」で登録。問診票へは「本人の申告、未確認」として反映。誤った元候補を無条件に出さない。

### E2E-004 別院アクセス

施設Aで権限を持つユーザーが施設BへのDelivery IDにアクセス。サーバ側で拒否し、存在の有無も区別できない。拒否の監査イベントのみ記録。

### E2E-005 退会と復元

退会要求後は全更新が拒否。取消可能期間内は再認証で復帰。30日経過後は全関連コレクション・GCS・Authが削除され、バックアップ復元しても削除済みデータを再公開しない。

### E2E-006 病院が直前に受信停止

患者が施設ページを開いた後、施設運営者が `receivingEnabled=false` にする。患者が送信ボタンを押すと412。既存Deliveryには影響しない。
