# 0017. バックエンドエミュレータ結合テスト基盤（DI・失敗注入・実行分離）

- ステータス: 承認
- 日付: 2026-11-07
- 作成者: Devin
- 関連: #25, docs/06, ADR-0013（メール登録の冪等・修復）, ADR-0014（監査）

## コンテキスト

#25 で「Vitest＋Firebase エミュレータ接続の結合テスト骨格」と
ネガティブ・冪等・失敗注入テスト、CI 接続を整備した。
設計上の制約・前提は以下。

- 既存ユニットテストは `MemoryFirestore` と各種 fake（DI 済 `Deps`）で
  399 件を超えており、本番コードを変えずに結合経路を追加したい
- `FirestoreLike` は `Pick<Firestore, "doc"|"collection"|"collectionGroup"|"runTransaction"|"batch">`
  であり、実 Admin SDK の `Firestore` がそのまま適合する（事実）
- エミュレータ接続テストが誤って実プロジェクトへ接続する事故は
  医療データを扱う本システムでは許容できない（仮説ではなくリスクとして扱う）
- 登録処理（ADR-0013）は Auth↔Firestore の分散失敗・再開を前提に設計されており、
  in-memory 実装では再現できない tx 失敗・Auth 例外の注入が必要

## 検討した選択肢

| 選択肢 | 概要 | 利点 | 欠点・犠牲になる点 |
|---|---|---|---|
| A. 実 Admin SDK を `Deps` に注入（採用） | `createEmulatorDeps()` が emulatorAdmin() の Firestore/Auth を返し、Storage/queue/gateway 等は既存 fake を維持 | 本番コード無変更。DI 層の差替だけで「実FSの tx/index/serverTimestamp 挙動」を検証できる | Admin SDK 経由のため Security Rules は評価対象外（#24 で別途カバー） |
| B. firebase-admin 全体をモック | `firebase-admin` を vi.mock して挙動を模倣 | エミュレータ不要 | Firestore セマンティクスの再現は自前になり検証価値が低い |
| C. REST/クライアントSDK経由で結合 | rules-unit-testing 型のクライアント視点 | Rules 込みで検証できる | Admin SDK 経路（本番と同じ権限）を外れ、API 層の検証としては不適 |

| 接続先の安全策 | | | |
|---|---|---|---|
| A. fail-closed + allowlist（採用） | `FIRESTORE_EMULATOR_HOST`/`FIREBASE_AUTH_EMULATOR_HOST` が未設定・非ループバック・不正形式なら throw。projectId は `demo-` 接頭辞のみ | 実プロジェクトへの暗黙接続を構造的に排除 | エミュレータ起動忘れ時は即エラー（Makefile が事前 curl で案内） |
| B. env を信用 | 設定された値をそのまま使う | 実装が短い | `.env` 混入・CI 変数ミスで本番接続し得る |

| CI でのエミュレータ起動 | | | |
|---|---|---|---|
| A. `emulators:exec`（採用） | `npx firebase-tools@15.35.0 emulators:exec --only auth,firestore --project demo-mmr-dev "npm --prefix services/api run test:emulator"` | 起動→テスト→自動終了が1コマンド。`singleProjectMode` と整合 | firebase-tools を毎回解決（バージョンは固定ピン） |
| B. compose サービスを CI で起動 | docker compose up で常駐起動 | ローカルと同一経路 | CI での Java/ポート管理・終了処理が煩雑 |

## 決定

1. **DI 注入は実 Admin SDK**。`test/helpers/emulator.ts` の
   `emulatorAdmin()` が `demo-mmr-dev` 単一 Admin アプリを生成し、
   `createEmulatorDeps()` で `deps.db`（`FlakyFirestore` 経由の実 Firestore）・
   `deps.authAdmin`（realAuth 指定時は `FlakyAuthAdmin` 経由の実 Auth）を注入。
   それ以外の外部依存（Storage/queue/gateway/logger 等）は既存 fake のまま。
2. **接続先は fail-closed**。ループバック（`localhost`/`127.x`/`::1`/`0.0.0.0`）以外の
   host、未設定、不正形式は全て throw。`demo-` プロジェクト接頭辞を強制。
   再利用する default Admin app の `projectId` も検証する。
3. **失敗注入は DI 境界のみ**。`FlakyFirestore.runTransaction` の回数制御
   （`failNextTransactions`）と `FlakyAuthAdmin` のメソッド別
   `failNext` カウントで Auth↔Firestore 間の部分失敗を再現する。
   本番コードに注入用フックは追加しない。
4. **実行分離**。`vitest.emulator.config.ts` で `test/integration` を専用実行し、
   `fileParallelism: false`（単一エミュレータ DB をファイル間で共有するため）。
   既定 `npm test` からは除外し、`npm run test:emulator`（CI/明示実行）と
   `test:emulator:compose`（compose ポート固定）を用意。
5. **テスト間の分離は emulator REST の削除 API**（Auth accounts・Firestore documents）
   で行い、決定的 UID/ドキュメント ID を使う。ID トークン検証は
   `FakeAuthVerifier` のまま（検証対象は Admin SDK 経路であり署名検証ではない）。

## 理由

- DI 層の差替は本番コードを一切変更せず「実 Firestore の tx・index・
  serverTimestamp・クエリ挙動」を検証できる最小の構成。
  実際、本基盤の追加直後に「同意書 tx コミット後の Auth 有効化失敗 →
  再試行で `legalConsents` 二重発行」という in-memory では再現し得ない
  実バグを検出できた（別 commit で修正済み、詳細は結果・影響）。
- fail-closed の allowlist は「設定ミスがそのまま本番接続になる」最悪系を
  構造的に排除するため。`demo-` 接頭辞は Firebase の demo プロジェクト
  （永続化なし・実データ無関係）制約と一致する。
- `fileParallelism: false` は共有エミュレータ DB への並列アクセスによる
  テスト間干渉を防ぐ唯一の方法。直列でも 2 ファイル 21 件が数秒で完走する。

## 結果・影響

- 追加資産: `services/api/test/helpers/emulator.ts`,
  `test/integration/registration.emulator.test.ts`（Auth↔Firestore 修復）,
  `test/integration/flows.emulator.test.ts`（E2E-001〜006 サーバ側観点・
  冪等・同意ゲート・IDOR・レート制限）, `vitest.emulator.config.ts`
- CI: `.github/workflows/ci.yaml` に `api-emulator` ジョブ
  （Node 22・Java 21・`firebase-tools@15.35.0`・timeout 15 分）
- ローカル: `make test-api-emulator`（エミュレータ起動確認つき）、
  `docs/09_USEFUL_COMMANDS.md` §6 に手順
- **本番修正を伴う検出**（テスト基盤整備の副産物）:
  - 同意 tx コミット後に Auth 有効化が失敗した場合、台帳巻き戻り経路で
    `legalConsents` が二重発行され得た → tx 内で account+同意書の
    コミット済み実在を確認し `already_committed` として再開するよう修正。
    main 側の #170（台帳 `preserved_checkpoint` 強化）とマージ統合し、
    「台帳が TTL 期限切れ上書きで `reserved` に戻った」経路のみを
    この実在ガードが担う形になった
  - `reconcileEmailConflict` が `getUserByEmail` の全例外を握りつぶして
    いたのを `auth/user-not-found` のみに限定（一過性 Auth 障害を
    恒久的 409 に誤分類しない）
  - 別 UID の disabled Auth ユーザー（孤児候補）の削除回収は #170 で
    意図的に廃止された動作のため、結合テストは「削除せず 409」を固定。
    別 Idempotency-Key 再試行が詰む残存ケースは #208 でフォローアップ
- Admin SDK 経由のため Security Rules・ID トークン署名検証は
  本テストの対象外（それぞれ #24・認証層テストが担う）

## 再評価条件

- エミュレータの負荷・起動時間が CI 実行時間の問題になった時
  （service container 方式等への移行を検討）
- Security Rules 込みの結合テストが必要になった時
  （クライアント SDK 併用の別レイヤ追加を検討）
- `test/integration` が増えて直列実行が遅くなった時
  （エミュレータ複数起動・project 分離による並列化を検討）
