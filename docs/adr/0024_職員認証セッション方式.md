# 0024. 職員認証セッション方式（HttpOnly Cookie + BFF プロキシ）

- ステータス: 承認
- 日付: 2026-11-15
- 作成者: Devin
- 関連: docs/02_システム設計書.md (SEC-05/SEC-06/NFR-05), apps/hospital, services/api

## コンテキスト

H-001（職員ログイン）では Firebase Auth の ID トークンを職員ポータルのサーバ処理と API 呼び出しに使う必要がある。ブラウザにトークンを永続化すれば XSS での窃取・持ち出しリスクが残り、一方でトークンを一切使わない方式は Firebase Auth の検証モデルと相容れない。セッションの持ち方・CSRF 対策・API アクセス経路を統一しないと、画面ごとに認証の抜けが生じる。

## 検討した選択肢

| 選択肢 | 概要 | 利点 | 欠点・犠牲になる点 |
|---|---|---|---|
| A | ID トークンを HttpOnly `__Host-mmr-session` Cookie に保持し、ブラウザ JS は同一オリジンの `/api/hx/*` BFF 経由でのみ API を呼ぶ | トークンが JS の手を介さず XSS 耐性が高い。サーバ側で MFA クレーム・所属検証を一元化できる | BFF ルートの実装・保守が必要。Cookie の SameSite/CSRF 設計が必須 |
| B | ブラウザの Firebase SDK が Bearer で直接 API を呼ぶ（ADR に近い患者側と同型） | 実装が最小 | トークンを JS 領域に置く必要があり、医療機関ポータルの脅威モデルに対して弱い |
| C | Next.js 側でセッション Cookie 方式（独自署名・サーバ検証）を新設 | トークンを外部に出さない | 自前のセッション管理は検証・失効処理の実装量が大きく、Firebase 側の失効と同期しにくい |

## 決定

A を採用する。

- ログイン: `signInWithEmailAndPassword` → 未登録なら TOTP 登録、`auth/multi-factor-auth-required` なら TOTP 検証を必須とする。
- セッション確立: `POST /api/session` が受け取った ID トークンを実 API の `GET /v1/me/facility-memberships` で検証し、有効時のみ HttpOnly・SameSite=Strict・Secure（本番）Cookie に保存する。
- API アクセス: ブラウザは `/api/hx/*` のみを呼び、Route Handler が Cookie から credential を取り出して `Bearer` + `X-Firebase-AppCheck` として API へ転送する。
- CSRF: SameSite=Strict に加え、必須カスタムヘッダー `x-hx-client: portal`・`Sec-Fetch-Site` 同一オリジン・`Origin` ホスト一致を Route Handler 側で強制する。
- ガード: `proxy.ts` は Cookie の有無だけで楽観的リダイレクトを行い、本検証は `(workspace)/layout.tsx` が `/v1/me/facility-memberships` 呼び出しで行う。認可は常に API 側の `facilityMemberships` が正本。
- 更新: クライアントは Firebase `onIdTokenChanged` 監視・定期更新・visibilitychange 時の再確立で Cookie を ID トークン寿命（約60分）より短い 55 分で更新する。Firebase Auth は `inMemoryPersistence` のためブラウザ再読み込みでは Firebase 側認証状態が消失し、Cookie も消去して再ログインになる（意図的なトレードオフ: JS 永続領域に refresh token を置かない）。
- 失効処理: `(workspace)/layout.tsx` が API の 401/403 を受けた場合、RSC からは Cookie を消せないため `GET /api/session/logout`（SameSite 確認付き）へリダイレクトして Cookie を消してから `/login` へ戻る。これにより「失効済み Cookie が残り /login と /facilities を往復する」ループを防ぐ。
- MFA のサーバ確認: `POST /api/session` は API 検証後に ID トークンの `firebase.sign_in_second_factor` クレームを確認し（本番のみ）、未 MFA の credential では Cookie を発行しない。クライアント側のチェックは UX 用の追加防御。

## 理由

- 患者側（Bearer 直叩き）と脅威モデルが違い、職員ポータルではトークンがブラウザ JS に露出しない方が XSS 被害を抑えられる。
- MFA 必須（NFR-05）を Cookie 書き込み前にクライアント側で検査し、かつセッション確立時に実 API で credential の有効性を確認する二重防御にできる。
- `facilityMemberships` を経由しない Cookie だけでの認可判断を排除でき、SEC-06 の「施設所属はサーバ側検証」に一致する。

## 結果・影響

- 認証系 Route Handler（`/api/session`, `/api/hx/*`）は `portalJson` で `no-store` を強制し、Proxy は認証後画面に `private, no-store` を付ける。
- クライアント側で ID トークンを localStorage 等へ永続化しない。Firebase Auth のブラウザ永続化は `inMemoryPersistence` のままとし、再読み込みは再ログインとなる。
- セッションの有効性確認は API 側に依存するため、API 障害時は業務画面に進めない（フェイルクローズ）。
- 本 ADR は #82 のセッション基盤に対応する。H-002 以降の画面も同一経路を使う。

## 再評価条件

- Firebase Session Cookie（`createSessionCookie`）や Identity Platform の長期セッションを導入する場合、トークン保持方式を再検討する。
- BFF が複雑化した場合は API 側の認可・監査の責務と齟齬がないか確認する。
