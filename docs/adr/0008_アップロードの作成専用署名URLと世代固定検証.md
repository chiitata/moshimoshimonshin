# 0008. アップロードの作成専用署名URLと世代固定検証

- ステータス: 承認
- 日付: 2026-11-06
- 作成者: Devin
- 関連: 03_機能仕様書（FR-M01/M06）, 06_医療安全_セキュリティ_運用設計書（SEC-07）

## コンテキスト

API-019 は Firebase Cloud Storage への直接アップロード用に V4 署名 URL を
発行し、API-020 はアップロードされた実オブジェクトをサーバ側で検証して
`uploaded` に遷移する。初期実装では署名 URL に新規作成限定の条件がなく、
`complete` 後に同じ URL を再利用すれば検証済みオブジェクトを別内容で
上書きできた。この場合、Firestore に残る `generation` とスキャン結果は
実際の内容を表さなくなり、OCR 入力の真正性が崩れる。

## 検討した選択肢

| 選択肢 | 概要 | 利点 | 欠点・犠牲になる点 |
|---|---|---|---|
| A. `x-goog-if-generation-match: 0` を署名対象ヘッダに含める | 署名 URL 自体に create-only 前提を埋め込む | サーバ側チェック不要・改ざん不可・GCSネイティブ | クライアントがヘッダ送信を省略すると 412（実装契約の周知が必要） |
| B. オブジェクト単位のバケットIAM/条件付きポリシー | GCS 側で上書き禁止を強制 | アプリ実装不要 | 署名URLの権限モデルでは新規作成のみ許可を表現しにくく複雑 |
| C. complete 時に「発行後の再署名」を禁止するだけ | URL を1回だけ有効にする管理 | 実装が小さい | 検証済みオブジェクトの不変性は保てず、証跡と実体の乖離は残る |

## 決定

**A** を採用する。

- 本番の署名 URL 発行時に `extensionHeaders` として
  `x-goog-if-generation-match: 0` を指定し、同ヘッダを `UploadUrlInstruction.headers`
  に含めてクライアントへ返す（署名対象のため値の差し替えは不可）
- `complete` はオブジェクト検査（存在・サイズ・Content-Type・マジックバイト）に
  合格した `generation`/`md5` を `uploads` ドキュメントに記録する
- 検査不合格のオブジェクトは実体削除せず空内容で上書き（tombstone）する。
  実体削除すると generation が解放され、有効期限内の同一 URL で
  `ifGenerationMatch: 0` が再び成立して拒否済みパスを再作成できてしまう
- 枚数上限（`uploadMaxActive`）は冪等トランザクション内の新規作成パスでのみ
  判定し、`expiresAt` 切れのドキュメントはカウント対象外とする

## 理由

- 検証済みアップロードが患者・第三者に差し替えられないことが、
  OCR 候補と問診提出物の真正性の前提になる
- 冪等リプレイが上限判定で失敗するとリトライ設計が破綻するため、
  判定は「新規作成のみ」に限定した

## 影響

- クライアントは署名 URL への PUT で `content-type` と
  `x-goog-if-generation-match: 0` の両ヘッダを必須送信する
- 既存オブジェクトへの再 PUT は GCS が 412 で拒否する（意図どおり）
- rejected オブジェクトは空ファイルとしてパスに残る（ライフサイクル規則で
  後始末する）。クライアント視点では再 PUT は 412 のまま変わらない
- `uploads(patientUid, status, expiresAt)` の複合インデックスを追加

## 再評価条件

- 再アップロード導線（差し替え要求）を許可する要件が出た場合
- バージョニング保有ポリシー等、別の不変性担保手段へ移行する場合
