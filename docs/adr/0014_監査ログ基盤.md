# 0014. 監査ログ基盤（auditEvents・イベント命名・PHI排除・シンク転送）

- ステータス: 承認
- 日付: 2026-11-13
- 作成者: Devin
- 関連: 06_セキュリティ設計書 §6, 04_DB設計書 §5.12, 02_アーキテクチャ図（WORK→AUDIT）, ADR-0009

## コンテキスト

医療系データを扱う本システムでは、「誰が・いつ・何を閲覧/送信/変更したか」の
証跡が規制・インシデント調査の双方で必須である。06 §6 は監査イベントの
収集を要件化し、04 §5.12 は `auditEvents` コレクションのスキーマを定義する。

一方で監査記録そのものが漏洩経路にならないよう、以下を両立させる必要がある。

- 患者UID・問診ID・メールアドレス等の直接識別子を監査に残さない
- 問診本文・症状・薬剤名など PHI を監査 details に含めない
- 監査基盤の障害で診療業務（問診確定・同意・アップロード）を止めない
- 状態遷移と証跡の一貫性（トランザクションがロールバックされた操作を
  「成功した操作」として記録しない）

## 検討した選択肢

| 選択肢 | 概要 | 利点 | 欠点・犠牲になる点 |
|---|---|---|---|
| A. 生IDを保存し、アクセス制御で保護 | auditEvents に uid/問診IDをそのまま書く | 調査時に join しやすい | 監査DBが侵害された時点で患者紐付けが全て漏れる |
| B. HMAC-SHA256 で一方向ハッシュ化 | `auditUidHash`/`auditResourceHash` で安定ハッシュ | 同一主体の行動追跡は可能・逆引き不可 | ハッシュキー管理が必要・外部 join には別途写像が要る |
| C. 監査失敗を業務エラーにする | 書込失敗時に API を 5xx にする | 証跡の欠落が起きない | 監査基盤の障害が診療業務を直撃する |
| D. 監査をベストエフォート化＋失敗をエラーログ | 業務は継続・失敗は構造化ログで検知 | 可用性を損なわない | 監査書込が欠落し得る（アラートで補完） |

## 決定

**B + D** を採用し、以下の構成とする。

1. **識別子の HMAC 化**: `actorUidHash`・`resourceIdHash` は
   `hmacSha256Hex(hmacSecret, "audit-uid:" + uid)` /
   `hmacSha256Hex(hmacSecret, "audit-res:" + id)` で生成する。
   `resourceIdHash` フィールドに生IDを入れてはならない。
   既に HMAC 済みの不透明値（登録操作の `operationHash`）はそのまま使ってよい。
2. **イベント命名の正本**: `src/domain/auditEvents.ts` の `AUDIT_ACTIONS`
   に全イベント名を登録し、`AuditEventDoc.action` を `AuditAction` 型で
   拘束する。SNAKE_UPPER 統一（過去に `intake.finalized` 等の
   ドット区切りが混在していたため）。
3. **発行方式の使い分け**:
   - `audit(deps, ev)`: 非トランザクション経路（閲覧・ワーカー結果・
     認証失敗）。書込失敗は `logger.error` で記録し業務を継続する。
     書込成功時のみシンク転送用構造化ログ `logAuditEvent` を出す。
   - `auditInTransaction(tx, deps, ev)`: 状態遷移と証跡を同一
     Firestore トランザクションに含める（同意受諾・退会申請/取消）。
     戻り値のイベントを**コミット確定後**に呼出側が `logAuditEvent`
     で出力する。ロールバック時に幻の監査イベントをシンクへ流さないため。
     Firestore は競合時に execute を再試行するため、収集配列は
     execute 冒頭でリセットし、最終試行分のみを出力する。
   - 冪等リプレイ（`runIdempotent` が過去応答を返す経路）では
     状態遷移が起きていないため監査も発行しない
     （`replayed` フラグで抑制）。例外は `UPLOAD_INIT` のみで、
     リプレイでも署名URLが新規発行される事実を `outcome: "url_reissued"`
     として残す。
4. **Security Audit Sink 連携**: `logAuditEvent` は
   `jsonPayload.auditEvent` フィールドにイベント全体を載せて
   `logger.info` する。Cloud Logging のシンクがこのフィールドを
   フィルタ条件にして別プロジェクトの監査保管先へ転送する想定
   （02図 WORK→AUDIT）。`occurredAt` は ISO 8601 に正規化して出力する。
5. **閲覧監査の記録条件**: `INTAKE_READ` / `OCR_EXTRACTION_READ` は
   所有確認を通過した読み取りのみ記録する。他人のリソースへの
   アクセスは 404 で秘匿され監査には残さない（存在秘匿とログ量抑制の
   両立）。認証失敗 `AUTH_FAIL` は Bearer を提示して検証に失敗した
   場合のみ記録し、`actorUidHash` は付けない（トークンを信用
   できないため）。また AUTH_FAIL の書込は未認証段階のため
   ルートのレート制御を通らず、トークンSpamによる Firestore 書込
   コストの増幅経路になる。これを防ぐため監査書込自体を
   `authFailAudit` ルール（30 req/min/IP）で制限し、超過時は
   401 応答のみ返して監査は落とす。
6. **ワーカー終端化の網羅**: OCR ジョブでは claim トランザクションが
   リース切れ・attempt 上限超過を検出して `worker_interrupted` で
   終端化する経路があり、通常の `finish()` を通らない。この経路でも
   `OCR_JOB_FAILED` を発行するため、claim 結果を `terminalized`
   kind として通常の `already_terminal`（既終端・発行済み）と区別する。
   削除ジョブでも同様に claim tx が `claim_abandoned` で終端化する
   経路を `terminalized` outcome で区別し `ACCOUNT_DELETION_FAILED`
   を発行する。削除ジョブのステップ失敗は `ACCOUNT_DELETION_FAILED`
   （retryable/terminal を outcome で区別）、期限超過アラートは
   `DELETION_JOB_OVERDUE` として `ACCOUNT_PURGED` と区別する。
   SLO-07 アラートのアンカーは `requestedAt + 猶予期間`（当初の削除
   予定時刻）とし、リトライで前進する `executeAfter` には依らない。
   `status: "failed"` の終端失敗ジョブもスキャン対象に含め、
   アラートマーカーは未設定ガード付きトランザクションで原子的に
   立ててから監査を発行する（重複アラート防止）。
7. **PHI 禁則**: `details` にはエラー分類・結果コード・クライアント
   種別など安全なメタデータのみを入れる。問診本文・症状・診断名・
   薬剤名・氏名住所・パスワード・トークン・署名URL・処方箋画像URLを
   含めない。テストで `JSON.stringify(audit)` に症状文字列が
   含まれないことを検証する。

## 理由

- HMAC 化により、監査ストア単体の漏洩では患者の行動履歴を復元できない。
  一方で同一ハッシュの連続は同一主体の行動追跡を可能にし、
  インシデント調査の主目的は維持される
- ベストエフォート方式は「監査のために診療を止める」本末転倒を防ぐ。
  欠落リスクは構造化ログへの二重出力とログベースのアラートで緩和する
- トランザクション内書込＋コミット後ログの分離により、「DBには無いが
  シンクにはある」という逆方向の不整合を防ぐ
- 命名の正本を型で強制することで、イベント名の表記ゆれによる
  集計・シンク設定の破綻を未然に防ぐ

## トレードオフ・影響

- `resourceIdHash` から生IDへの逆引きには、調査時に元コレクションを
  走査してハッシュ照合する手順が必要（件数が多い場合の運用手順は
  別途 runbook で扱う）
- `audit()` のベストエフォート性により、Firestore 障害と同時に
  監査が欠落し得る。構造化ログが GCP 側に残るため二次証跡として
  機能するが、ログとDBの完全一致は保証しない
- 閲覧監査は成功した読み取りのみ記録するため、「存在しない/他人の
  リソースへの探索的アクセス」は auditEvents には残らない。
  その種の検知はアプリケーションログの 404 集計で行う
