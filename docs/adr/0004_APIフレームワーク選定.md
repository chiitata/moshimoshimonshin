# 0004. APIフレームワーク選定（Fastify）

- ステータス: 承認
- 日付: 2026-11-08
- 作成者: Devin
- 関連: docs/02_システム設計書.md §11, docs/07_環境構築手順書.md, ADR-0001

## コンテキスト

`services/api`（Cloud Run 相当の Node.js + TypeScript API）のWebフレームワークを選定する必要があった。
要件:

- PHI を扱う医療系サービスのため、構造化ログ（request-id 相関・PHI 非含有）と
  堅牢なエラー形式が第一級で必要
- Firebase Emulator 連携のローカル Docker 開発と Cloud Run 本番の両対応
- ルート単位の認証/認可/同意/レート制御を一貫適用できる拡張点
- Zod によるリクエスト検証との相性
- `tsx watch` + Compose Watch によるホットリロード

## 検討した選択肢

| 選択肢 | 概要 | 利点 | 欠点・犠牲になる点 |
|---|---|---|---|
| A. Fastify 5 | 成熟した Node.js WebFW | pino 構造化ログが組込み。`config`/`addHook` でルート単位のアクセス制御宣言が自然に書ける。`inject()` でネットワーク不要のテストが可能。Cloud Run 実績多数 | middleware ではなく hook モデルに慣れが必要 |
| B. Hono | 軽量・Web標準Fetch API準拠 | 薄い・速い・Edge 移植性 | App Check/Admin SDK 系の実績とエコシステムが Fastify より浅い。構造化ログは自前で組む必要がある |
| C. Express | 最も普及したFW | 情報量・採用実績 | 構造化ログ・型安全は自前組合せ。非同期エラー処理が煩雑 |
| D. Cloud Functions 直書き | Functions のHTTPトリガ | デプロイが単純 | ローカル開発・責務分割・テストがしにくい。Compose 連携の要件と合わない |

## 決定

**A. Fastify 5** を採用する。Zod 検証・標準エラー形式・冪等キー・レート制限は
`preHandler` hook（`enforceAccess`）に集約し、ルートは `config.access` で
利用階層（public/internal/authenticated/consented/active）を宣言する。

## 理由

- pino ロガーが組込みで、PHI を含めない構造化ログ・request-id 相関が設計どおり実装できる
- `app.inject()` によりエミュレータ不要の密閉ルートテストが書ける（`test/routes`）
- プラグイン/デコレート拡張が成熟しており、Admin SDK・App Check・独自 DI を素直に統合できる
- 医療安全の観点で、認証→App Check→状態・同意→認可→レート制御の検証順を
  一つの hook に集約でき、ルート追加時の適用漏れを構造的に防げる

## 結果・影響

- `src/app.ts` が hook・エラーハンドラ・ルート登録を担い、`src/index.ts` は
  config→Firebase 初期化→deps 組立て→listen のみのエントリになった
- テストは `test/` 配下にまとめ、インメモリ Firestore 偽装 + `app.inject` で実行
- 本番のルーティング認証（Cloud Tasks OIDC 等）は infra issue #31 で置き換え予定

## 再評価条件

- Firebase Genkit/Functions へ全面移行する判断が出た場合
- エッジ実行（Workers 等）への移行要件が確定した場合
