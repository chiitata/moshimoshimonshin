# 0006. ローカル開発のソース同期をバインドマウントへ変更

- ステータス: 承認
- 日付: 2026-11-06
- 作成者: Devin
- 関連: ADR-0001（本 ADR がソース同期方針の一部を置換）, docs/08_Docker_Makefile運用.md

## コンテキスト

ADR-0001 では `services/api`・`apps/hospital` のソース同期に
Compose Watch の `sync`（＋ `package.json` の `sync+restart`）を採用した。
実運用で以下の設計上の問題が判明した:

1. `sync+restart` は watch 起動時の初回にも発火する。初期 sync 直後にコンテナが
   再作成され `/app` が空に戻り、起動時 `npm install` が package.json 不在で失敗して
   コンテナが終了。以降 watch は差分のみを sync するため復旧しない（永久に空）
2. `docker compose watch` は起動時に未変更ファイルを初期 sync しない。
   コンテナ再作成後に watch を再起動しても `/app` は空のまま
3. macOS バインドマウント越しの inotify がコンテナ内に届かない環境がある

## 検討した選択肢

| 選択肢 | 概要 | 利点 | 欠点・犠牲になる点 |
|---|---|---|---|
| A. バインドマウント＋コンテナ内 tsx watch | `./services/api:/app` をマウントし、`node_modules` のみ named volume で分離 | 同期遅延・初期 sync 問題が消失。tsx がコンテナ内で変更を検出して自動再起動 | package.json の依存追加は `make restart-api` が必要（コンテナ起動時の `npm install` に任せる） |
| B. Watch の sync+restart をやめ sync のみ＋手動 restart | `sync+restart` による `/app` ワイプを回避 | watch の枠組みは残せる | 未変更ファイルの初期 sync 問題は残り、コンテナ再作成後に `/app` が空になる不具合は解消しない |
| C. Mutagen など外部同期基盤 | 双方向同期を別デーモンで管理 | 高信頼 | 依存ツールが増え、Compose 標準で完結しない |

## 決定

**A** を採用する。`services/api`・`apps/hospital` はバインドマウントでソースを
コンテナへ直接供給し、`node_modules` は named volume に隔離する。
`develop.watch` の API/hospital 向けルールは撤去した。

firebase エミュレータの `firebase.json`・`firebase/` に対する
`sync+restart` ルールは変更のたびにコンテナ内ファイルが再作成される用途であり、
`/app` ワイプ問題と無関係なため **維持**する。

## 理由

- ホスト側保存 → コンテナ内 tsx watch 検出 → 自動再起動の経路が単純で、
  Compose Watch のバージョン差・初期 sync 仕様に依存しない
- `/app` を空にする根本原因（sync→restart ループ）が構造的に消える
- 依存追加だけはコンテナ起動時 `npm install` に委譲する運用で吸収できる

## 結果・影響

- 依存を追加した場合は `make restart-api`（または `make restart-hospital`）を実行する
- `make watch-start`/`stop-watch`/`logs-watch` は firebase エミュレータ向けの
  watch のみを制御する（api/hospital のソース反映には不要）
- docs/07・docs/08 のファイル反映表を実態どおり更新済み

## 再評価条件

- Compose Watch が未変更ファイルの初期 sync に対応し、restart ループの
  制御手段（初回抑制フラグ等）が提供された場合は見直しの余地がある
