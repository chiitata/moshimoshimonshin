# 0023. 審査用架空デモの方針

- ステータス: 提案
- 日付: 2026-11-06
- 関連: [文書一覧](../README.md)、[ADR 一覧](README.md)

## コンテキスト

約4日程度で動作する審査用デモが必要である。従来の文書には実患者・実施設・正式運用を想定した要件が含まれるが、今回のデモはそれらの完成を目標としない。審査用に公開環境を使う予定のため、架空データであっても公開範囲や誤接続等のリスクに対応する。

## 選択肢

- 正式運用に必要な要件をすべて満たしてから提供する。
- 架空データと模擬連携で審査用デモを先行し、正式運用を別の段階とする。

## 決定

後者を採用する。患者・施設・問診内容は架空のものを使用し、外部施設連携・配送等は模擬する。実患者情報、実施設の非公開情報、実通知、実際の診断・治療・予約は扱わない。画面や手順には架空デモであることと実行されない操作を明示する。正式な規約・同意文書は後日用意するものとし、仮の文書を正式な同意取得として扱わない。

患者アプリの現行デモでは、症状・問診文は固定の架空サンプルで、自由入力・編集はできない。利用者が選べるのは身体部位のみであり、その選択だけを根拠に問診内容を架空とみなすものではない。利用者の実際の症状は入力しない。患者・施設・同意・症状の例は架空で、固定施設への操作は画面上の模擬送信に限る。実送信・永続保存・正式な同意取得は行わず、選択状態はアプリ内メモリにのみ保持する。このデモは API の `fixedQuestions` による問診経路とは別であり、同 API の固定質問セットを実行するものではない。

公開前には、実際の配信方法・対象・期間に応じ、アクセス制限、秘密情報の保護、入力・リクエスト量の制限、ログの最小化、実サービスへの誤接続防止を確認する。現時点で公開経路・対象・期間は未確定であり、この ADR は対策の実装・検証や公開の完了を意味しない。実環境の作成・設定変更・課金は別途承認を要する。

公開前の担当者は、対象・公開期間・停止方法を定め、以下を実装とテストまたは設定確認で検証し、結果と未解決事項を記録する。重要な確認が未了のまま公開しない。公開範囲に応じて対策を選び、不要な本格運用機能をデモの完成条件にはしない。

- デモ用の接続先と設定を明示し、実サービスの認証情報を使わず、実サービスへの誤接続を拒否する。使うサービスに応じて接続先制限や環境分離を検証する。
- 審査者に実際の患者情報等を入力しないよう表示する。自由入力が不要なら設けず、必要なら入力の保存先・ログ混入・保持期間・削除方法を確認する。
- 審査対象者に応じたアクセス制限、秘密情報の露出防止、公開エンドポイントの入力と負荷の上限、審査終了後の停止・データ削除を確認する。検索除外設定はアクセス制限の代替としない。

旧文書は履歴として保持する。今回のデモに適用する要件は更新版を正とし、旧文書の正式運用向け要件を自動的にデモの完了条件としない。ただしデモの公開安全性を省略する根拠にもならない。正本の所在と各資料の適用範囲は文書一覧に明示する。

## 結果・トレードオフ

短期間で主要な体験を確認できる一方、模擬連携の結果は実施設への送信や受領を証明しない。Firebase や Web の実行環境がアセット等を取得する可能性もあるため、模擬操作とネットワーク通信全般を混同しない。デモと実運用の差異は手順・画面・テスト結果で区別する。

## 再評価条件

実データ、実施設、実通知または実サービスへの接続を導入する場合は、この決定を見直す。正式運用への移行前には、正式文書、本人確認・認可、実データの保護、連携・障害対応等を別途設計・承認・検証する。
