# 0015. FCM通知送信基盤（文言カタログ・PHI非含有・トークン失効処理）

- ステータス: 承認
- 日付: 2026-11-13
- 作成者: Devin
- 関連: 01 FR-O01/O05, 02 §10（FCM）, 04 §5.15/§6.2, ADR-003, ADR-011, ADR-0014

## コンテキスト

OCR完了・問診票確定など非同期処理の完了を患者へ知らせるため、FCM による
プッシュ通知基盤が必要である（FR-O01）。一方で通知ペイロードは端末上の
OS通知領域・FCM事業者を経由するため、以下を両立させる必要がある。

- タイトル/本文に症状・病名・薬剤名・個人情報を載せない（FR-O05, ADR-011）
- 通知送信が業務処理（OCR・確定）の成否を左右しない
- トークン失効（再インストール・FID移行）で送信を続けない
- 患者別の進捗状態を RTDB（シンガポール）に置かない（ADR-003, 04 §6.2）

## 検討した選択肢

| 選択肢 | 概要 | 利点 | 欠点・犠牲になる点 |
|---|---|---|---|
| A. 呼び出し側が自由文を指定 | 各処理が title/body を渡す | 柔軟 | PHI混入を全呼出箇所で防がねばならずレビュー不能 |
| B. 文言カタログ＋data制限（採用） | `NOTIFICATION_TEMPLATES` の固定文言のみ。dataは `type`/`refId` のみ | 構造的にPHI非含有。ペイロードに呼出由来の文字列が存在しない | 新しい文言はカタログ追加（コード変更）が必要 |
| C. Firestoreトリガー型Cloud Functionsで送信 | 02 §9.2 の通知ジョブ案 | APIプロセスと分離 | 本リポジトリにFunctions基盤がなく新規構築になる |
| D. API内ベストエフォート送信（採用） | 状態遷移コミット後に同プロセスで送信 | 既存の監査発行パターンと一致・単純 | 送信失敗時の再送は次回イベントまで遅れ得る |

## 決定

1. **文言カタログ**: `services/notifications.ts` の
   `NOTIFICATION_TEMPLATES` に一般文言のみ登録し、呼び出し側は
   テンプレート名と `refId`（不透明docID）のみを指定できる。
   `assertCatalogPayload` が送信直前に title/body がカタログ登録値と
   完全一致するか検査し、カタログ外文字列の混入を実行時にも遮断する。
2. **デバイス管理**: `pushDevices/{deviceId}` に登録。
   `deviceId = "pdv_" + HMAC(secret,"push-device",token)` の決定論的IDで
   再登録を冪等化。トークンはアプリインストールに紐づくため、
   同一トークンを別アカウントが登録した場合は最後の登録者が受信者となる。
   登録/解除は API-042/043（active tier、POSTは Idempotency-Key 必須）。
   解除は所有者確認と削除を同一トランザクションで行い、読み取り後の
   所有権移動（別アカウントの再登録）で他人の端末を消さない。
   退会時は DeletionWorker の authAccount/residualScan が
   `patientUid` で一括削除する。
3. **送信**: `PushGateway` IF を Deps に注入。本番は Admin SDK
   `messaging.send`、エミュレータは `DisabledPushGateway`
   （`disabled` を返し、トークン保持・監査記録なしのスキップ扱い）。
   送信は状態遷移コミット後のベストエフォートで、失敗は
   `NOTIFICATION_FAILED` 監査+warnログのみ（業務を止めない）。
   冪等リプレイ・無遷移の経路では通知しない（監査と同一条件）。
4. **トークン失効**: FCM エラーを分類し、
   `registration-token-not-registered` / `installation-id-not-registered`
   → `unregistered`、`invalid-registration-token`
   → `invalid_token` はデバイスを `invalid` に更新して以後の送信対象外。
   `invalid-argument` はメッセージレベルの汎用エラーでありトークン起因
   とは限らないため `unknown`（誤無効化しない）。
   `server-unavailable` 等の一時障害は `active` のまま保持する。
   無効化はトランザクション内で `lastSeenAt` を再照合し、
   送信試行後の再登録を `invalid` で上書きしない。
5. **RTDB**: 患者別の通知状態・進捗は書かない（04 §6.2）。個別進捗は
   API応答（polling）で返し、RTDBは引き続き `publicOperationalStatus`/
   `operationalCounters` の非PHI運用状態のみ。
6. **監査**: `PUSH_DEVICE_REGISTERED`/`PUSH_DEVICE_UNREGISTERED`/
   `NOTIFICATION_SENT`/`NOTIFICATION_FAILED` を auditEvents に記録。
   details は `template`・`platform`・`errorCode` のみで文言・トークン・
   生IDを含めない。

## firebase-js-sdk#10135 への考慮

クライアントが `httpsCallable`（Cloud Functions SDK）を呼ぶと、SDK内部で
旧式トークンが `Firebase-Instance-ID-Token` ヘッダ用に発行され、
FIDベースのpush登録が失効する既知の問題がある
（https://github.com/firebase/firebase-js-sdk/issues/10135）。

- 本APIは REST/Cloud Run であり callable は使わないため、サーバ側で
  この不具合を直接発生させる経路はない。
- ただし FID ベース登録が外部要因で失効し得る前提で、
  `messaging/installation-id-not-registered` も `unregistered` として
  分類しトークンを無効化する（静黙失効への恒久対処）。
- 患者クライアント側の留意点として、Web版で Functions SDK を併用する
  場合は旧式トークンの再登録で登録が潰れ得ることを ADR に記録する。
  クライアントは本APIへの `fetch`/REST 呼び出しを使い、
  callable 併用時はトークン再登録の再発に注意する。

## 理由

- PHI非含有を「呼び出し側の注意」ではなく構造で強制できる（テストで担保）。
- 決定論的 deviceId でトークンローテーション・再登録・冪等リプレイが
  同一docに収束し、二重送信や孤児docを防げる。
- ベストエフォート送信は ADR-0014 の監査パターンと同じ可用性原則
  （通知基盤の障害で診療操作を止めない）に従う。

## トレードオフ・影響

- FCM一時障害時の再送機構（outbox/Cloud Tasks）は初期実装に含めない。
  `NOTIFICATION_FAILED` 監査で観測し、必要になれば SLO-03 の outbox
  パターンで再送経路を追加する。
- OCR失敗時の通知は現時点で送らない（完了のみ）。失敗の周知は
  processing API の状態で行う。
- `PUSH_DEVICE_SEND_LIMIT=20` で送信増幅を抑止する。登録doc数自体の
  上限は設けないが、deviceId がトークン由来の決定論的IDのため
  蓄積は個別トークンの発行数で頭打ちになり、登録APIのレート制限と
  退会時の一括削除で実用上のコストは抑えられる。

## 検証

- `test/services/notifications.test.ts`: カタログペイロード構築、
  カタログ外文言の拒否、全activeデバイス送信、unregistered/invalid_token
  でのinvalid化、unavailableでのactive保持、disabledでのスキップ
  （監査なし）、再登録競合時の非上書き、監査の非PHI。
- `test/routes/devices.test.ts`: API-042/043 の登録・冪等・409・404秘匿。
- `test/workers/deletionJob.test.ts`: 退会ジョブが pushDevices を削除する。
- `test/workers/ocrJob.test.ts`: 成功時のみ通知、終端再実行で再送しない。
- `test/routes/intakes.test.ts`: finalize での通知とリプレイ非重複、
  ペイロードに症状文字列を含まないこと。
