# 0023. HXデザインシステムの実装方式（Tailwind @theme トークンと共通コンポーネント）

- ステータス: 承認
- 日付: 2026-11-15
- 作成者: Devin
- 関連: docs/10_デザインシステム.md, apps/hospital

## コンテキスト

apps/hospital（Next.js 16 + Tailwind CSS v4）で、デザインシステム `docs/10_デザインシステム.md` のHX仕様をコードへ落とす必要があった。トークンの持ち方・コンポーネント境界・検証方法を統一しないと、画面ごとの色・サイズ直書きや一貫性のないアクセシビリティ実装が生じる。

## 検討した選択肢

| 選択肢 | 概要 | 利点 | 欠点・犠牲になる点 |
|---|---|---|---|
| A | Tailwind v4 `@theme` でトークンを定義し、`hx-*` ユーティリティを生成。トークン単一ソースは globals.css | ユーティリティ名がトークン名に一致し、直書き色値をレビュー・検索で検出しやすい。ビルド時に使う色だけが出力される | セマンティック命名規約をチームで維持する必要がある |
| B | デザインシステム通りの `:root` CSS変数ファイル＋任意値 `bg-[var(--hx-color-primary)]` | ドキュメント命名と完全一致 | 任意値ユーティリティが長く読みにくい。Tailwind側の型安全/補完が効かない |
| C | styled-components 等の CSS-in-JS | コンポーネント単位で閉じる | 新規依存・RSCとの相性・ランタイムコスト。リポジトリ方針に反し過剰 |

## 決定

A を採用する。`app/globals.css` の `@theme` に `--color-hx-*`・`--text-hx-*`・radius トークンを定義し、共通コンポーネントを `components/design-system/` の `Hx*` コンポーネントに集約する。未認証ページの共通ヘッダーは `components/layout/portal-header.tsx` とし、認証後シェル（`HxAppShell`）とヘッダー構造を連続させる。状態ラベルの唯一の対応表は `DELIVERY_STATUS` とする。コンポーネントの状態確認は開発限定の `/dev/catalog` で行う。

## 理由

- 医療安全: 状態色だけに意味を持たせない・必須を文字で明示する等の規約を、コンポーネント API（`required` プロパティ、バッジの label 必須）として強制できる。
- 一貫性: 色・タイポグラフィをトークン経由に限定し、直書きを構造的に減らせる。
- アクセシビリティ: フォーカスリング・aria 紐づけ・スキップリンクを共通部品側で一度だけ正しく実装できる。
- 依存: 追加ライブラリを増やさず、既存の Tailwind v4 の機能だけで実現できる。

## 結果・影響

- 画面実装（H-001〜H-006）は `Hx*` コンポーネントを組み合わせて作る。新しい意味色・タイポロールが必要なら globals.css のトークン追加から行う。
- `DELIVERY_STATUS` を変更する場合は `docs/10_デザインシステム.md` §17.5 と整合させること。`delivered` のトーンは §17.5 の `warning/neutral` 選択肢に対し、§4.4「未受領を注意色で煽らない」に従い `info` を採用した。未定義の状態値は成功系へ誤表示しないよう中立の「不明」で示す。
- `HxAppShell` のサイドバーは §6.3 のブレークポイント（<1024px ドロワー / 1024–1199px アイコンレール72px / 1200–1439px 220px / ≥1440px 240px）に従う。
- 本番ビルドで `/dev/catalog` は 404 になる。開発中の視覚確認用途に限定する。

## 再評価条件

- 患者向け UI（PX トークン）を同アプリへ同居させる必要が出た場合、トークン名前空間の分離方式を再検討する。
- Storybook 等の専用カタログ基盤を導入する場合、`/dev/catalog` の役割を移行する。
