# 0016. 運営管理API（施設審査・受付停止・失敗ジョブ一覧）

- ステータス: 承認
- 日付: 2026-11-13
- 作成者: Devin
- 関連: 01 FR-H04/FR-O04, 03 §2 O-001/O-002・API-036〜038, 04 §5.8/5.8.1, ADR-0014

## コンテキスト

運営者（platform_security_admin）向けに、施設審査・受付停止・障害監視の
管理APIが必要である（#20, API-036〜038）。制約は以下の通り。

- 審査未承認施設には問診票を送信できないこと（受入条件・安全側）
- FR-H04: 実在・申請者・受信担当者・所在地の検証証跡を残す
- FR-O04 / O-002: 失敗ジョブ一覧はPIIを原則表示しない
- 運営操作は全て監査すること
- 緊急停止は即効性と安全性の両立が求められる

## 検討した選択肢

| 選択肢 | 概要 | 利点 | 欠点・犠牲になる点 |
|---|---|---|---|
| A. Custom Claims で運営権限 | ID token の custom claim に admin flag | 高速・DB読取不要 | 権限剥奪が即時反映されない（token寿命まで有効） |
| B. facilityMemberships 正本（採用） | `role=platform_security_admin` の active membership で判定（既存 `requirePlatformSecurityAdmin`） | 失効が即時反映・02 §5.3の「URL/claim を権限証明にしない」原則と一致 | 毎リクエスト membership 読取（rate limit内で許容） |
| C. verify で審査のみ分離 | verificationStatus と receivingEnabled を独立管理（採用） | 緊急停止が審査再審査なしに即効・責務分離 | 停止→再開に別操作が要る |
| D. disable で suspended にもする | 審査状態と受付を同時に止める | 一操作で完全停止 | 審査（真正性）と運用キルスイッチを混同。誤停止の復旧が重い |

## 決定

1. **権限**: `authenticated` tier + `requirePlatformSecurityAdmin`
   （facilityMemberships の `role=platform_security_admin`・`status=active`
   を照合）。変更系 POST は `requireFreshAuth`（高リスク操作の再認証）も必須。
2. **API-036 verify**: 4検証項目の `checks`（全て true 必須・スキーマで強制）
   と `verificationRecordId`（検証文書参照・必須）を受け、同一txで
   施設docを `verified` + `facilityVerificationRecords` に証跡docを作成。
   既承認は409、`suspended/rejected` からは再承認可。
   `receivingEnabled` は触らない（承認と受付の責務分離）。
3. **API-037 disable**: `reason` 必須。`receivingEnabled=false` と
   `receivingDisabledAt/reason` を施設docに記録。審査状態は変更しない。
   既停止は冪等成功・監査なし（遷移なし＝監査なし、ADR-0014と同条件）。
4. **API-038 job-failures**: `type=ocr|deletion` 必須で失敗ジョブを
   `{type, jobId, failureCode, attempts, failedAt}` のみ返す。
   patientUid/subjectUid/uploadId 等の個人紐付け識別子は一切含めない。
   スナップショットカーソルでページングし、対象外・失効カーソルは空ページ。
   なお `ocrJobs` の doc ID は uploadId そのものではなく
   `oj_`+HMAC(hmacSecret, "ocr-job:"+uploadId) の擬名とする
   （create-if-absent の決定性は維持）。これにより jobId 経由で
   uploadId が漏れることを構造的に防ぐ。
   さらに、ハッシュ化以前に作成された旧形式doc（doc ID = uploadId）が
   残っていても漏れないよう、レスポンス境界でも防御する:
   - `jobId` が `oj_[0-9a-f]{64}` 形式でない行は同一HMACスキームで
     再擬名化してから返す。
   - `nextCursor` はスナップショットカーソルのdocパスを
     AES-256-GCM（hmacSecret 派生鍵）で暗号化した不透明トークンとし、
     改竄・他用途・対象外コレクションは復号失敗→空ページ（fail-closed）。
   削除ジョブのIDはランダムauto-IDで非識別のため生値を返す。
5. **監査**: `FACILITY_VERIFIED` / `FACILITY_RECEIVING_DISABLED` /
   `JOB_FAILURES_LISTED` を発行。`actorType:"platform"`、
   actorUidHash/resourceIdHash は HMAC 済みのみ。
   details は `{from, recordId}` / `{from}` / `{type}` のみで
   自由記述（reason/note）や生IDを含めない。

## 理由

- 未承認施設への送信不可は deliveries 側の既存ゲート
  （`verificationStatus==="verified"` かつ `receivingEnabled`）が保証して
  おり、本APIはそのフラグを安全側に操作するだけで送信経路を変えない。
- verificationStatus（真正性）と receivingEnabled（運用キルスイッチ）を
  分離することで、緊急停止が即効かつ審査再審査なしに行える。
- 失敗ジョブ一覧は識別子を不透明IDのみに絞り、運営が障害を追跡しつつ
  患者PIIを一切見られない構造にする。

## トレードオフ・影響

- 受付再開の経路は本スコープ外（H-006 の施設側受付設定・または将来の
  enable API）。誤停止時は運営がDB直接操作するか将来APIで対処する。
- 失敗ジョブ一覧は `type` ごとの単一コレクションページングのみ
  （全種混合タイムラインは2リクエストで合成する）。
- 停止理由は施設docに残すが監査detailsには含めない
  （監査の自由記述混入を構造的に抑止）。
