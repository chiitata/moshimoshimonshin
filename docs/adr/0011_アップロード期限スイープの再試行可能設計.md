# 0011. アップロード期限スイープの再試行可能設計

- ステータス: 承認
- 日付: 2026-11-06
- 作成者: Devin
- 関連: ADR-0008（作成専用署名URL）, 03_機能仕様書（FR-M06 保管期限）

## コンテキスト

`/v1/internal/jobs/upload-expiry-scan`（Scheduler 呼び出し）は期限切れの
`pending`/`uploaded` アップロードを `expired` に遷移させ、Storage 上の実体を
tombstone 化する。初期実装には二つの欠陥があった。

- クエリが `expiresAt <= now` のみを条件とし、既に `expired` 済みの終端
  ドキュメントも limit（既定200）を消費する。終端 doc が溜まると後続の
  本当に期限切れの doc へ永遠に到達しない
- `expired` 化と tombstone の間に失敗状態がない。tombstone が一時障害で
  失敗すると、doc は既に終端のため次回スキャンで対象外となり、
  原本オブジェクトが保管期限を超えて残置する

また `complete` が期限切れを検出して `expired` にする経路でも、Storage
オブジェクトの後始末がなかった。

## 検討した選択肢

| 選択肢 | 概要 | 利点 | 欠点・犠牲になる点 |
|---|---|---|---|
| A. クエリに status を含め、`objectCleanup` フィールドで再試行状態を保持 | 対象絞り込みをクエリ側に移し、tombstone 成否を永続化 | 進行停止・残置の双方を構造的に解消。実装が小さい | フィールド追加と複合インデックスが必要 |
| B. ページネーションで終端 doc を読み飛ばす | limit 消費を回避 | フィールド追加なし | tombstone 失敗の再試行は解決しない |
| C. 失敗時にジョブキューへ別タスクを投入 | Cloud Tasks で個別再試行 | 即時性 | ジョブ状態とキュー状態の二重管理が複雑 |

## 決定

**A** を採用する。

- スキャンクエリは `status in (pending, uploaded)` AND `expiresAt <= now`
  とし、終端 doc が limit を消費しない（`uploads(status, expiresAt)`
  複合インデックスを追加）
- `uploads.objectCleanup`（`pending`/`done`）を導入。`expired`/`rejected`
  への遷移時に `pending` を立て、tombstone 成功時に `done` へ更新
- スイープは `objectCleanup == "pending"` の doc も拾い、tombstone を
  再試行する（sweep・complete・reject の全経路で統一）

## 理由

- 「後始末が残っている」ことを永続化しない再試行は、一時障害を永続的な
  残置に変える。PHI を含み得る画像の保管期限超過は医療安全上のリスク
- 状態をクエリ条件に含めることで、件数が増えてもスキャンが常に前進する
  ことを Firestore レベルで保証できる

## 影響

- `upload-expiry-scan` の応答は `{ scanned, expired, cleaned }`
- tombstone に成功するまで doc は `pending` のまま残り、運用上
  「クリーンアップ滞留」として監視可能

## 再評価条件

- オブジェクト削除ポリシーが tombstone から実体削除へ変わる場合
- クリーンアップを専用ワーカーへ分離する要件が出た場合
