# 0013. ヘルスチェックの依存状態プローブ

- ステータス: 承認
- 日付: 2026-11-06
- 作成者: Devin
- 関連: 03_機能仕様書（API-040, §4.2 UPSTREAM_UNAVAILABLE）, issue #21

## コンテキスト

API-040 `GET /healthz` は LB/monitor scope の内部ヘルスチェックとして、
プロセス存活だけでなく**依存状態**を返す必要がある（issue #21）。
既存実装は `{status:"ok", service, emulator}` の固定応答で、Firestore が
落ちていても 200 を返し続け、LB が異常インスタンスへ振り続ける欠陥があった。

同時に `/healthz` は認証なしの公開経路であり、依存障害の詳細を外部へ
漏らしすぎないこと、LB チェック間隔を阻害しない高速性が求められる。

## 検討した選択肢

| 選択肢 | 概要 | 利点 | 欠点・犠牲になる点 |
|---|---|---|---|
| A. liveness 固定200 + readiness 別経路 | `/healthz` はプロセス存活のみ、依存確認は `/readyz` 等へ分離 | LB と監視で意味を分離できる | 経路・インフラ設定が増える。現段階では LB/monitor 双方が同一エンドポイントを見る設計 |
| B. `/healthz` に依存プローブを内包、失敗時 503 | Firestore 読み取りを短時間で試し、結果を `checks` に含める | 1経路で LB が異常インスタンスを外せる。仕様の「依存状態」を直接満たす | プローブ失敗時は当該インスタンスが外れるため、Firestore 全体障害で全台が外れる（= 意図通り） |
| C. 全外部依存（Auth/Storage/Tasks/Places）を逐一プローブ | 網羅的な readiness | 検出範囲が広い | 外部API課金・レイテンシ増大・失敗の原因切り分けが曖昧。Firestore が正本であり最小で十分 |

## 決定

**B** を採用する。

- `/healthz` は `{status, service, emulator, checks: {firestore}, checkedAt}`
  を返す。`checks.firestore` は `ok | error`
- Firestore プローブは `appConfigs/publicLegalVersion` の read 一回、
  タイムアウトは `HEALTHZ_PROBE_TIMEOUT_MS`（既定 2 秒）。ドキュメント
  有無ではなく read の成立を確認する
- プローブ結果は `HEALTHZ_PROBE_CACHE_MS`（既定 5 秒）インスタンス内で
  キャッシュする。期限切れ時の同時到着は進行中プローブを共有し
  （single-flight）、単一インスタンス内で Firestore read を 1 回に束ねる。
  これにより認証なし公開経路の要求集中が課金対象の read に直結しない。
  `Cache-Control: no-store` を付け、経路上のキャッシュが障害・復旧を
  隠さないようにする
- `/healthz` はアクセス階層を `tier: "none"` と明示宣言する
  （認証・App Check・レート制限なし）。`none` 以外の未宣言 `/v1/*`
  ルートは fail-closed で 500 とし、宣言漏れによる意図しない公開を防ぐ
- プローブ失敗時は `status="degraded"`・HTTP 503。degraded も標準
  エラー封筒ではなくヘルス応答スキーマで返す（監視が `checks` を常に
  同じ形で読めるようにするため）
- 依存の詳細エラー（例外内容・原因）は応答に含めず `ok | error` に留め、
  詳細はサーバログ（warn, requestId 相関）のみとする

## 理由

- 正本データが読めないインスタンスは業務 API を正常に処理できないため、
  LB/monitor が検知して外せることが医療安全・可用性の観点で必須
- プローブ対象を Firestore に限定したのは、本サービス全業務データの
  正本であり、Auth/Storage 個別障害は部分劣化として別監視で扱う方が
  誤検知が少ないため
- 公開経路で例外詳細を返すと内部構成情報の露出になり得るため、
  応答は ok/error の二値に留める

## 結果・影響

- Firestore 障害時に LB が当該インスタンスを外す。Firestore 全体障害時は
  全インスタンスが 503 となりサービス全体として停止扱いになる
- 監視側は `checks.firestore` の推移で依存別の劣化を追跡できる
- `/v1/public/legal-documents`（API-039）も併せて強化した:
  必須同意一覧の欠落・未知/非文字列種別・必須種別の文書欠落/版・
  ハッシュ不備・Firestore 読取失敗はいずれも `retryable: true` +
  `Retry-After` 付きの 503 `UPSTREAM_UNAVAILABLE` とし、設定不備を
  成功応答に見せない。`Retry-After`（15 秒）は失敗キャッシュ TTL
  （10 秒）を超える値とし、案内された再試行が同一失敗を引かない
  ようにする。障害・設定不備はサーバログ（warn, requestId
  相関）に残す。応答の文書キーは既知の `CONSENT_TYPES` に限定し、
  文書フィールドは `version/documentHash/publishedAt` の
  ホワイトリストに正規化して運用メタ等の混入を公開面から遮断する。
  応答は `Cache-Control: no-store` とし、版ローテーションの伝播を
  経路キャッシュが遅らせないようにする。読取は起動時集中を見越して
  インスタンス内 10 秒キャッシュ＋single-flight とし（失敗も
  キャッシュ）、同意提出・評価側は fresh read を維持する。専用レート
  `RateRules.publicRead`（60 req/分/IP）を適用し、Cloud Run/GFE が
  唯一のイングレスという前提の下で直近 1 ホップのみを信頼する
  `trustProxy` でクライアント IP 単位の制限を維持する
  （CGNAT 配下の起動時集中を想定。GFE 以外の直接経路があると
  XFF 偽装で回避されるため、イングレス制限はインフラ側の前提条件）
- 法務設定の不備は同意評価・提出側でもサーバ障害として扱う。
  `requiredConsents` の非配列・空・未知種別は `getLegalDocuments` が
  `undefined` を返し既存の fail-closed（500 INTERNAL）経路に流す
  （空配列への正規化は同意評価の空ループ vacuous pass = fail-open を
  招くため採用しない）。必須種別の文書/メタ欠落は
  `evaluateConsents`・`validateConsentSubmission` で 500 INTERNAL とし、
  「再同意しても解決不能な状態」を 412 というクライアント起因
  エラーに見せない。一方 `getLegalDocuments` の読取自体が
  例外で失敗する場合（Firestore 障害）は設定不備ではなく一時障害
  として、`evaluateConsents`・`registration`・`onboarding` の各
  呼出経路で 503 `UPSTREAM_UNAVAILABLE`（`retryable: true`）に
  変換する。`ApiError` による 5xx 応答は `sendError` で warn ログに
  記録し、意図的なサーバ障害が監視から見えなくならないようにする
- アクセス階層の fail-closed は「実際にマッチした `/v1` ルートの
  宣言漏れ」に限定し、未登録パスは従来通り 404 とする
  （スキャンやタイポが 500 アラートを汚染しないように）

## 再評価条件

- LB と詳細監視で責務を分けたくなった場合（`/healthz` を liveness 固定に
  戻し `/readyz` を新設する選択肢 A への移行）
- Storage/Places 等の部分劣化も LB 除外条件に含めたい要件が出た場合
