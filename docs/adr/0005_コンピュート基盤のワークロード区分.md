# 0005. コンピュート基盤のワークロード区分

- ステータス: 承認
- 日付: 2026-11-06
- 作成者: Devin
- 関連: docs/02_システム設計書.md §2.6・§10, ADR-0004

## コンテキスト

本プロダクトのサーバサイドは複数のワークロード種別を持つ:
HTTP API、Firestore/RTDB/Storage のイベント駆動処理、FCM/メール送信、
外部サービスの Webhook 受信、AI 問診チャット（ストリーミング・長時間）、
問診票生成・変換、重いバッチ処理、定期実行、退会削除ジョブ。

各ワークロードをどの実行基盤（Cloud Functions for Firebase / Cloud Run /
Cloud Run Jobs / Cloud Scheduler + いずれか）に載せるかを確定する必要があった。
Cloud Functions 第2世代は内部実装が Cloud Run であるため、
ここでの区分は「実行基盤」ではなく「プログラミングモデルとトリガ方式」の選択である。

## 検討した選択肢

| 選択肢 | 概要 | 利点 | 欠点・犠牲になる点 |
|---|---|---|---|
| A. イベント駆動=Functions／API・AI・バッチ=Cloud Run／定期実行=Scheduler→Functions | ユーザ提案の区分 | トリガ宣言が最短・低ボイラープレート | 定期実行だけ起動経路が API 実装と別系統になり、削除ジョブの Scheduler→Tasks→Cloud Run 設計と二重化する |
| B. A だが定期実行は Scheduler→Cloud Run | 定期実行も API 側の内部エンドポイントに統一 | 定期実行・削除スキャン・Tasks 呼び出しが同一の内部ジョブ経路（認証・監査・冪等）に集約できる | Functions にも同等のジョブを置きたくなった場合に規律が必要 |
| C. すべて Cloud Run | イベント駆動も Eventarc/PubSub→Cloud Run | ランタイムが1つ | トリガ毎の Pub/Sub・Eventarc 配線を自前で保守する必要があり、イベント駆動の実装コストが増える |
| D. すべて Cloud Functions | API もバッチも関数化 | 構成が単純 | AI チャットのストリーミング・長時間実行・Fastify 実装資産・Compose ローカル開発との相性が悪い |

## 決定

**B** を採用する。ワークロード区分は以下のとおり:

| ワークロード | 実行基盤 | 起動方式 |
|---|---|---|
| Firestore 更新を契機とした通知 | Cloud Functions for Firebase（第2世代） | Firestore trigger |
| FCM プッシュ通知・メール送信 | Cloud Functions for Firebase | Firestore/キュー trigger |
| 外部サービスの Webhook | Cloud Functions for Firebase | HTTPS trigger |
| AI による問診チャット | Cloud Run | HTTPS（API エンドポイント） |
| 問診票生成・変換 API | Cloud Run | HTTPS（API エンドポイント） |
| 病院向け管理 API・患者向け API | Cloud Run | HTTPS（Fastify、`services/api`） |
| 重いバッチ処理 | Cloud Run Jobs | 手動/スケジュール実行 |
| 定期実行（削除スキャン等） | Cloud Scheduler → Cloud Run | 内部エンドポイント（OIDC） |
| 退会削除ジョブ（issue #8） | Cloud Scheduler → Cloud Tasks → Cloud Run | `/v1/internal/jobs/*`（実装済み） |

Functions 側の処理も本設計の認可・監査・冪等・PHI 非含有の方針に従う
（docs/02_システム設計書.md §2.6 記載どおり）。

## 理由

- Firestore/RTDB/Storage のイベント駆動は Functions の trigger 宣言が最も
  ボイラープレートが少なく、Eventarc/PubSub の配線を自前保守する必要がない
- HTTP API・AI チャット・問診票生成は既存の Fastify/Cloud Run 実装
  （ストリーミング・長時間タイムアウト・並行制御）をそのまま使える
- 定期実行を Cloud Run の内部ジョブ経路に統一することで、
  削除スキャン（Scheduler→Tasks→`/v1/internal/jobs/*`）と同一の
  認証・監査・冪等制御を再利用でき、起動経路が二重化しない
- 削除ジョブ基盤は実装・検証済みの現行形態（Scheduler→Tasks→Cloud Run）を維持する。
  ステップ永続化・リトライ・クレームを備えており Functions 化の利点がない

## 結果・影響

- `services/api`（Cloud Run）が API・AI・定期実行・削除ジョブの受け口を担う
- FCM/メール/通知/Webhook 系は別途 `functions/`（Cloud Functions for Firebase）に
  実装する見込み。同じ認可・監査・PHI 方針を適用すること
- 内部エンドポイントの本番認証は infra issue #31（Cloud Tasks OIDC）で強化予定。
  現行は `INTERNAL_JOB_TOKEN` による共有トークン認証（エミュレータ/テストでは緩和）

## 再評価条件

- Functions 側にも定期実行や重バッチが必要になった場合
- Eventarc の成熟度・コスト特性が変わり C の全面 Cloud Run 化が有利になった場合
- AI チャットのリアルタイム要件（LiveKit/WebSocket 等）が Cloud Run の適合範囲を超えた場合
