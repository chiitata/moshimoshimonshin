# 0027. 施設受付停止の主体記録と正式情報の再審査導線

- ステータス: 承認
- 日付: 2026-11-15
- 作成者: Devin
- 関連: docs/03_機能仕様書.md (H-006), docs/10_デザインシステム.md (17.14), services/api/src/routes/hospitals.ts, apps/hospital/app/(workspace)/settings

## コンテキスト

H-006 は施設設定（正式名・宛先確認・受付停止）を施設管理者へ開放する。既存の受付停止 API（API-037 `/operator/facilities/{id}/disable`）は `platform_security_admin` 専用の緊急停止であり、施設管理者による運用停止とは主体・目的が異なる。同時に、正式名称・所在地は患者の宛先確認の正本であり、デザインシステム 17.14 は「第三者の信頼に関わる項目は自己申告だけでは変更不可。再審査フローへ誘導」と定める。

## 決定

1. **受付停止/再開は施設管理者自身の API とした（API-049 `PATCH /hospitals/{facilityId}/settings`）**
   - `facility_admin` + 直近認証（`requireFreshAuth`）を要求する。
   - 患者側の送信可否判定（BR-07）は `receivingEnabled` 単一フィールドを見るため、施設側の停止も同じフィールドに書き、患者側表示との整合を自動的に保つ。
   - 施設側の停止は理由を必須とし、`receivingDisabledAt`/`receivingDisabledReason` に記録する。再開時はこれらをクリアする。

2. **停止主体を `receivingDisabledBy: "platform" | "staff"` で記録する**
   - 運営の緊急停止（API-037）は施設側で解除できては意味をなさないため、`platform` による停止を施設管理者が再開しようとした場合は 409 で拒否し、画面でも運営への問い合わせを案内する。
   - 既存データ（`receivingDisabledBy` 未設定）は安全側の `platform` として扱う。
   - 施設自身による停止中に運営が緊急停止を実行した場合は、停止主体を `platform` へ引き上げて理由を運営のものに置き換える。引き上げないと施設側で再開でき、緊急停止が実効を失う。
   - 運営停止の解除導線は `POST /operator/facilities/{facilityId}/enable`（API-050、platform_security_admin + 再認証）とし、施設への問い合わせ案内と整合する解除経路を運営側にも用意する。
   - 再開は `FACILITY_RECEIVING_ENABLED`、停止は `FACILITY_RECEIVING_DISABLED` を監査に記録する（操作主体・理由・時刻が追跡可能。施設側の停止理由は再開で施設docから消えるため監査の details にも残す）。状態遷移のない PATCH は冪等成功とし監査を発行しない。
   - `receivingDisabledReason` は運営記録（非公開）のため、施設への返却は `receivingDisabledBy === "staff"`（施設自身が記入した値）に限定する。

3. **正式名称・表示名・所在地は API・画面ともに読み取り専用**
   - 宛先確認情報は運営審査済みの正本であり、自己申告での上書きを許すと審査の意味が失われる。設定画面では値の表示と「変更には運営の再審査が必要」という案内のみを提供する。

## 検討した代替案

- **施設側でも正式名等を直接編集でき、変更と同時に `verificationStatus=pending` に戻す案** — 審査済み正本を未審査の自己申告で上書きし、宛先確認表示を一時的にでも改竄可能にする。17.14 の「自己申告だけでは変更不可」に反し、患者保護の観点でも不適切として却下。
- **変更申請レコードを新コレクションに積み、運営承認で適用する案** — 理想的だが、運営側の承認 UI・通知経路まで新規実装が必要で H-006 の範囲を大きく超える。再審査導線（案内表示）で足りる現段階の要件として却下。将来の拡張候補。
- **`platform` 停止を施設管理者でも再開可能にする案** — 緊急停止の無効化に繋がるため却下。

## 影響

- 施設管理者は自院の受付を理由付きで制御でき、既受領の問診票は影響を受けない。
- 運営の緊急停止権限は施設側の操作で無効化されない。
- 患者側は `receivingEnabled` の変更を既存の施設情報 API・送信可否判定で即時に反映するため、送信不可時の患者側表示との整合が保たれる。
