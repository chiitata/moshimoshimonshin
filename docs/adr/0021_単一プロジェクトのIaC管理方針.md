# 0021. 単一プロジェクトのIaC管理方針

- ステータス: 提案（PR承認で確定）
- 日付: 2026-11-07
- 作成者: moshi_codex
- 関連: [Issue #28](https://github.com/chiitata/moshimoshimonshin/issues/28)、[Terraform再構築手順](../../infra/terraform/REBUILD.md)、[設計書 §13.1](../02_システム設計書.md)

## コンテキスト

PR #168でTerraform雛形が導入され、後続PRでStorage・監査等が追加されたが、Terraform採用比較と管理境界がADRに記録されていなかった。Terraformと手動gcloud/YAMLを同じ資源へ並行適用すると設定の正本が曖昧になる。

現行の運用指示は `project-7efcc4c4-6c86-490c-ba5` 一つを使用し、stg/prodを分けない。設計書の3環境構想よりこの実行範囲を優先し、別プロジェクトを作らない。これは医療データの投入承認や職務分離の完了を意味しない。

## 検討した選択肢

| 選択肢 | 再現性 | 管理コスト・制約 |
|---|---|---|
| gcloud手順書と宣言YAMLのみ | 実行順序と手作業の履歴に依存。既存スクリプトを利用できる | state不要だが、ドリフト確認・作成済み判定・複数資源間の依存解決を人が担う |
| Terraform＋境界を決めた専用CLI（採用） | tfに記述された資源の依存関係とplanを確認できる | provider/lockfile、remote state、import、stateアクセス権の管理が必要。全Firebase設定を一つのtfに押し込まない |
| 複数のIaCツールを同じ資源へ適用 | 書式ごとの既存資産を使える | 二重管理と設定の差し戻しを招くため不採用 |

## 決定

`infra/terraform/*.tf` に記述したGCP資源の設定はTerraformを正本とし、同じ資源へ従来のgcloud/YAMLを並行適用しない。緊急変更は差分を記録し、次のplanでコードへ反映してから通常運用へ戻す。

- Terraform: SA/IAM、Artifact Registry、Cloud Run設定、Tasks/Scheduler、Secretの箱とIAM、Firestore/PITR/バックアップ、画像bucket、監査bucket/view/sink。
- Firebase CLI/CD: Hosting、Firestore/Storage/RTDB RulesとFirestore indexes。
- 個別bootstrap: project/API有効化、Firebase登録、state bucket、Auth/App Check/RTDB、WIF。各担当runbookの正本を使う。
- Secretの値: Secret Manager。tfvars・state・PR・ログへ入力/表示しない。
- イメージ: CDが不変のSHA/digestで更新。既存tfのimage ignore_changesを維持する。

## 結果・影響

stateは対象project内の専用GCS bucketで管理し、versioning・限定アクセスとstate lockingを利用する。既存資源は新規作成せず、対応するtfアドレスへ一度だけimportし、planで差分を確認する。ローカルstateがある環境では無条件reconfigureをせず、管理者が移行対象を確認する。

stateはコードから除外した機密情報を含み得るため、plan/stateファイルもGitへ入れない。新規構築と既存環境の引継ぎの順序・検証はREBUILD.mdを正本とする。このADRは実環境のapply完了を主張しない。

## 再評価条件

別プロジェクトへの環境分離が明示的に承認された場合、Terraform管理対象が大幅に増えた場合、またはprovider対応により管理境界を変える必要が出た場合に後続ADRで見直す。
