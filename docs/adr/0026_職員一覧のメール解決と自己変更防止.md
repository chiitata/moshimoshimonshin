# 0026. 職員一覧のメール解決方式と管理者の自己変更防止

- ステータス: 承認
- 日付: 2026-11-15
- 作成者: Devin
- 関連: docs/03_機能仕様書.md (H-005), services/api/src/routes/staff.ts, apps/hospital/app/(workspace)/staff

## コンテキスト

H-005（職員管理）では施設管理者が所属職員と保留中の招待を一覧し、招待・役割変更・停止/再有効化を行う。招待・メンバーシップ更新 API は先行して実装済みだったが、画面が必要とする「職員一覧」の読み取り API がなかった。また `facilityMemberships` は `userUid`・`role`・`status` のみを保持し、表示に必要なメールアドレスを保持しないため、一覧表示には別途ユーザー情報の解決が必要だった。

## 検討した選択肢

| 選択肢 | 概要 | 利点 | 欠点・犠牲になる点 |
|---|---|---|---|
| A | 一覧 API が `facilityMemberships` と `facilityInvitations`（pending）を返し、メールは Firebase Auth `getUser` で都度解決。未登録ユーザーは `email: null` | メールの正本が Firebase Auth に一元化され、重複保存の不整合が起きない。一覧取得が Auth の個別失敗で落ちない | メンバー数分の Auth 参照が発生する（上限200件で制限） |
| B | 招待・メンバーシップ作成時にメールを `facilityMemberships` へ非正規化保存する | Auth 参照不要で高速 | メール変更時の同期が必要。PII の重複保存が増える |
| C | 一覧は `userUid` のみ返し、メール解決は別エンドポイントで行う | 一覧が軽い | 画面が N+1 呼び出しになり、UX と実装が複雑化する |

## 決定

選択肢 A を採用する。

- `GET /v1/hospitals/{facilityId}/staff` を追加し、`facility_admin` のみ許可する（`requireFacilityRole`）。施設 ID はクライアント入力ではなくメンバーシップ解決で認可する。
- メンバーは `facilityMemberships` の施設スコープ全件（上限200）、招待は `facilityInvitations` の `status=pending`（上限100）を返す。いずれも等値クエリのみで複合索引は不要。
- メールアドレスは `deps.authAdmin.getUser(uid)` で都度解決し、Auth 未登録・参照失敗は `email: null` にフォールバックして一覧を継続する。メールは権限判定に使わない。
- 管理者が自身のメンバーシップを停止・管理者以外へ降格することを API が 403 で拒否する既存仕様を維持し、画面側でも自分の行では操作を出さない（最終管理者喪失の防止）。さらに、有効な施設管理者が権限を失う変更では、トランザクション内で他の有効管理者の存在を確認し、ゼロになる場合は 409 で拒否する（2名の管理者が同時に互いを停止する競合でも管理者不在にならない）。
- 保存済みメンバーシップ・招待に職員以外のロールや未知の状態が混ざっていても、一覧はその行を警告ログ付きで除外して 200 を返す（1件の異常データが管理画面全体を 500 にしない）。
- メール解決の Auth 呼び出しは20件ずつのチャンクに制限し、Auth 参照の同時実行数を抑える。`auth/user-not-found` 以外の失敗は警告ログに残す（一覧の null 表示に障害が埋もれないようにするため）。
- 一覧は `userUid` を返すが、これは施設管理者が職員を識別・操作するために必要な範囲であり、施設外には露出しない。

## 結果・影響

- 職員管理画面（`/staff`）が実 API で完結し、招待・役割変更・停止・再有効化が行える。
- Auth 参照はメンバー数ぶん発生するため、大規模施設ではページング検討の余地がある（現行上限200件）。
- 退会済みユーザーは「メール未登録」として一覧に残り、管理者が停止操作で除去できる。
- メール変更は Auth 側の変更がそのまま一覧に反映される（スナップショット不整合なし）。
