# 0028. 配送作成時の施設別同意証跡のサーバ検証方式

- ステータス: 提案
- 日付: 2026-11-08
- 作成者: Devin
- 関連: docs/03_機能仕様書.md (§5.4 API-029, P-032), docs/04_DB設計書.md (§5.3, §5.10), docs/02_システム設計書.md (§9), ADR-0014, GitHub Issue #219, #72, #17

## コンテキスト

API-029 `POST /deliveries` は、従来クライアント申告の `consentDocumentVersion` 文字列をそのまま `delivery.consentId` へ保存していた。サーバは同意レコードの実在・版・hash・範囲・撤回状態を一切確認せず、患者がチェックを付けずに配送でき、P-032 で取得した個別同意が証跡として残らなかった（Issue #219）。

法務・医療安全上の要求は以下の通り。

- 第三者提供文書への同意は **患者・施設・送信内容・文書版** に紐づく実レコードとして存在し、配送と同一トランザクションで永続化されること。
- 配送レコードは同意記録を参照可能であること（クライアント申告文字列を `consentId` に保存してはならない）。
- 同意レコードの不存在・denied・旧版・hash 不一致・範囲不一致・撤回済みは拒否すること。
- 撤回と配送作成の競合、冪等リトライ、部分失敗でも一貫した状態になること。

なお、同意文書の正式文言・同意取得の UI 手順（P-032）・撤回 UX の要件は法務・医療安全担当の確認事項であり、本 ADR はサーバ側の検証・保存方式のみを決定する。

## 検討した選択肢

| 選択肢 | 概要 | 利点 | 欠点・犠牲になる点 |
|---|---|---|---|
| A | クライアントが事前に同意レコードを `legalConsents` へ作成し、配送 API がその `consentId` を tx 内で検証 | 同意取得と配送を分離できる | 同意作成の別 API/権限設計が必要。同意 doc 作成→配送までの間に内容を変えうる。deliveryId を後付けで紐づける必要があり円環参照になりやすい |
| B | 配送 API が `consent` 申告（accepted/version/hash/shareScope）を受け、サーバが現行文書と照合した上で同意レコードを配送 tx 内に作成 | 同意→配送の単一原子操作。deliveryId を採番してから書き込めるため円環参照がない。撤回検知 doc も同一 tx で更新できる | API 契約の変更（`consentDocumentVersion` → `consent` オブジェクト）。既存クライアントの追随が必要 |
| C | `consentDocumentVersion` 文字列のまま、サーバが申告版と現行版のみ照合 | 契約変更が最小 | 「誰がどの範囲に同意したか」の証跡が残らず、denied/撤回/範囲超過を検証できない。Issue の受入条件を満たさない |

## 決定

選択肢 B を採用する。

1. **リクエスト契約**: `consentDocumentVersion`（string）を廃止し、`consent` オブジェクト `{ accepted, documentVersion, documentHash, shareScope }` を必須とする。
2. **サーバ検証**（配送 tx 内、全 read を write 前に実施）:
   - `accounts/{uid}` を tx 内で読み `accountStatus == "active"` を確認（配送 tx in-flight 中の退会・停止や退会ジョブの consent 削除との競合を安全側に倒す）。
   - `appConfigs/publicLegalVersion` を tx 内で読み、`hospital_disclosure` の現行 `version`/`documentHash` を取得（版ローテーションとの競合を read→write 競合で安全側に倒す）。
   - `consent.accepted !== true`、version/hash が現行値と不一致、`shareScope` が `consent.shareScope` を超過する場合は 412 で拒否。
   - 施設別同意 state doc `legalConsents/fc_{subjectUid}_{facilityId}` を tx 内で読み、`subjectUid`/`scope.facilityId` の防御的照合を行い、`revokedAt != null`（撤回済み）または `decision == "denied"` なら 412 で拒否。同 doc を読むことで、本物の backend では撤回の同時書き込みが read→write 競合を起こし tx が再評価される（撤回レースで安全側に倒れる）。
3. **同意証跡の保存**（同一 tx で 2 doc）:
   - `legalConsents/fc_{subjectUid}_{facilityId}`: (uid, facilityId) 単位の同意 state doc（`registrationSource: "facility_consent"`）。送信のたびに `{merge: true}` upsert で最新の granted 状態・`scope.lastDeliveryId`/`scope.lastConsentId` を更新し、他フローが書いた項目を潰さない。撤回操作はこの doc の `revokedAt` を立てる。**撤回は終端的であり、`revokedAt` が立った doc は送信経路では granted に戻さない**（再同意は専用の撤回解除フローが別途必要。本 ADR スコープ外）。
   - `legalConsents/{autoId}`: 本送信固有の immutable 証跡（`registrationSource: "delivery_send"`）。`scope` に `facilityId`/`questionnaireId`/`questionnaireRevisionId`/`shareScope`（同意した範囲）/`sentShareScope`（実際に送信した範囲）/`deliveryId`/`facilityConsentId` を保持する。
   - いずれも `consentType: "hospital_disclosure"`, `method: "explicit_checkbox"`、`occurredAt: FieldValue.serverTimestamp()`（サーバ時刻の正本化）とする。`deliveryId` は doc 生成前に採番できるため円環参照は成立しない。
4. **配送レコード**: `delivery.consentId` は送信証跡 doc の ID、`consentDocumentVersion`/`consentDocumentHash` はサーバ照合済みの現行値、`facilityConsentId` は state doc ID。
5. **監査**: `DELIVERY_CREATED` の details に `consentIdHash`/`documentVersion`/`documentHash`（hash 化 ID・版・文書 hash のみ、PHI なし）。同意検証の拒否は新 action `DELIVERY_REJECTED`（decision=deny）を発行し、resource は state doc の hash、details に `reason`・申告 `documentVersion`/`documentHash` を記録する（PHI・生 ID なし）。同意検証以外の 412（施設停止等）では発行しない。
6. **冪等性**: 既存の `runIdempotent` 境界を維持する。同一キー再送は保存済み結果を再生し同意証跡を重複作成しない。tx リトライでは `committedAudits` を試行毎にリセットする。
7. **同意履歴の読み取り**: `GET /v1/consents` は送信証跡（`delivery_send`、1送信1件の高頻度書き込み）で登録系同意が押し出されないよう、`registrationSource` で履歴表示対象を絞り（`CONSENT_HISTORY_SOURCES`）、`currentByType` は履歴先頭100件ではなく `latestConsentsByType` の種別ごとクエリ（source 絞り込み付き）で解決する。必要な複合索引を `firebase/firestore.indexes.json` に追加する。

## 理由

- 「送信した」のではなく「同意した送信に基づき配送した」ことを証明できるのは、同意レコードと配送レコードを同一トランザクションに置く設計だけである（02 §9 のトランザクション境界要件）。
- クライアント申告はあくまで申告とみなし、文書版/hash の照合と state doc の撤回検知はサーバ保存値で行う。端末時刻・任意ハッシュでの上書きを防ぐ（04 §5.3）。
- state doc（`(uid, facilityId)` で一意・upsert）と送信証跡 doc（immutable・作成のみ）を分けることで、「現在この施設へ送ってよいか」の単一の撤回検知点と、「この送信について何に同意したか」の不変証跡を両立できる。

## 結果・影響

- `POST /deliveries` のリクエスト契約が変わる（`consentDocumentVersion` → `consent`）。患者アプリの P-032 実装（Issue #72 系）と hospital 統合テストを追随する。
- `GET /v1/consents` の `consents[]` は `delivery_send` の送信証跡を含まない履歴になる（表示対象の source のみ）。送信証跡自体は配送詳細の `consentId` から参照可能。
- 新規複合索引（`legalConsents`: subjectUid+registrationSource+occurredAt、subjectUid+consentType+occurredAt、subjectUid+consentType+registrationSource+occurredAt）を追加する。エミュレータは索引を要求しないため、本番では deploy 前の索引適用が必要。
- 撤回は終端的: `revokedAt` が立った施設では以後の配送作成は常に 412 になる。患者が再度同意して送れるようにするには、撤回解除を行う専用フロー（state doc の revokedAt クリア + 証跡）の実装が別途必要。
- `legalConsents/fc_{uid}_{facilityId}` の ID はアンダースコア連結であり、`_` を含む uid/facilityId の組み合わせでは理論上の衝突がありうる（`fc_a_b_c` = (a_b, c) or (a, b_c)）。読み取り側で `subjectUid`/`scope.facilityId` を照合して誤認を防ぐ。将来 ID 体系を変える場合は区切り不能なエンコードへの移行を検討する。
- 撤回操作のエンドポイントは未実装。実装時は `legalConsents/fc_{uid}_{facilityId}` を更新点とすること（この doc が配送 tx の撤回検知点である）。
- 配送拒否時に `DELIVERY_REJECTED` 監査が増える。拒否理由は enum の reason コードと申告版/hash のみで PHI を含めない。
- 本変更前の `deliveries.consentId` はクライアント申告文字列が混入しうる（旧契約）。既存データの consentId は送信証跡を指さない可能性があるため、表示・参照側は存在確認を行うこと。
- エミュレータは doc ロックで直列化するため本物の backend の ABORTED 再評価は再現できない。結合テストは「撤回と配送のどちらが先にコミットされても最終状態が一貫する」ことと「コミット前失敗で部分状態が残らない」ことを検証する。

## 再評価条件

- 撤回 UX・同意更新 API が実装され、state doc の書き込み主体が複数化した場合（書き込み経路の一元化を再検討）。
- 同一 tx の doc 上限（500）に近づくほど同意証跡が肥大化した場合。
- 同意文書の版管理が公開アーカイブ運用に変わり、version/hash 照合の正本が `appConfigs/publicLegalVersion` 以外へ移る場合。
