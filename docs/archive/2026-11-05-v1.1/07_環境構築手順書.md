# もしもし問診 — 環境構築手順書

- 文書ID：MMR-ENV-001 / v1.0 / 2026-11-05
- 対象：ローカル開発環境（macOS / Windows / Linux）
- 関連：`02_システム設計書.md`、`08_Docker_Makefile運用.md`、`adr/0001_ローカル開発基盤の構成.md`、`adr/0002_ローカルのシークレット管理.md`

本書はリポジトリをクローンしてから `make up` で全サービスが起動するまでの手順と、
環境変数・秘密情報の管理方針をまとめる。Docker/Makefile の詳細な運用（個別停止・再起動・
ログ・再ビルド・ファイル変更の自動適用）は `08_Docker_Makefile運用.md` を参照。

## 1. ローカル開発の全体像

```
[ホスト]  Flutter Web (患者アプリ)        http://localhost:5050   ← apps/patient 作成後に自動起動
[Docker]  hospital (Next.js+Tailwind CSS 病院ポータル) http://localhost:3000   ← apps/hospital 作成後に自動起動
[Docker]  api (Cloud Run API相当)         http://localhost:8080   ← services/api 作成後に自動起動
[Docker]  firebase (Emulator Suite)       http://localhost:4000   ← 常に起動
          ├ Auth      : 9099
          ├ Firestore : 8081 (コンテナ内 8080)
          ├ RealtimeDB: 9000
          └ Storage   : 9199
```

- **Firebase Emulator は本番GCPに接続しない**（プロジェクトIDはダミーの `demo-mmr-dev`）。実患者データ・実APIキーはローカルに置かない。
- アプリ実装（`apps/hospital`、`apps/patient`、`services/api`）がまだ無い場合、`make up` はエミュレータのみ起動し、実装が追加されると自動で起動対象に含める。
- 患者Flutterアプリは iOS/Android 実機開発のためDocker化せず、`make up` がホストで `flutter run -d web-server` を起動する（ADR-0001）。

## 2. 必要なツールと導入方法

| ツール | 用途 | 必須度 |
|---|---|---|
| Docker（Compose同梱） | エミュレータ・API・病院ポータル | 必須 |
| Make | 起動/停止の統合コマンド | 必須 |
| Flutter SDK（Dart同梱） | 患者アプリ（`make up` の patient 起動） | アプリ実装時に必須。stable 3.x系（詳細は§2.4） |
| Git | 取得 | 必須 |
| Node.js | Dockerを使わずAPI/Next.jsを直に動かす場合のみ | 任意 |

`make doctor` で導入状態をいつでも確認できる。

### 2.1 macOS

```bash
# Docker Desktop（Compose含む）: 公式サイトかHomebrew
brew install --cask docker
open /Applications/Docker.app   # 初回は起動してデーモンを待つ

# Make: macOS標準のBSD make (GNU Make 3.81) で動作確認済み。追加導入不要。
make --version

# Flutter（患者アプリ実装時。詳細なバージョン・PATH設定は §2.4）
brew install --cask flutter     # または公式zip + PATH設定
flutter doctor
```

### 2.2 Windows（WSL2推奨）

```powershell
# 1. Docker Desktop をインストール（Settings > Resources > WSL integration を有効化）
# 2. WSL2 で Ubuntu を入れる
wsl --install -d Ubuntu
```

WSL内（Ubuntu）で：

```bash
sudo apt update && sudo apt install -y make git
# DockerはWindows側のDocker DesktopをWSLから利用する（追加インストール不要）

# Flutter（患者アプリ実装時。詳細なバージョン・PATH設定は §2.4）
sudo snap install flutter --classic   # または公式tarball + PATH設定
flutter doctor
```

※ Windowsネイティブ（PowerShell）でも `winget install ezwinports.make` 等でMakeを入れれば動くが、WSL2側での運用を推奨する。

### 2.3 Linux（Ubuntu例）

```bash
# Docker Engine + Composeプラグイン（公式手順）
sudo apt update && sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo usermod -aG docker $USER   # 再ログインで反映

sudo apt install -y make git

# Flutter（患者アプリ実装時。詳細なバージョン・PATH設定は §2.4）
sudo snap install flutter --classic
flutter doctor
```

### 2.4 Flutter SDK の詳細（バージョン・PATH・ツールチェーン）

患者アプリ（`apps/patient`）の実装に必要。**Dart SDKはFlutterに同梱**されるため個別導入は不要。

#### 必要バージョン

| 項目 | 要件 |
|---|---|
| Flutter | **stable チャンネルの 3.x系**（本リポジトリの開発環境は `3.44.8` で動作確認） |
| Dart | Flutter同梱版をそのまま使用（`flutter --version` でDart版も確認できる） |

`apps/patient/pubspec.yaml` が作成されたら、そこの `environment.sdk` 制約が正式な基準になる。未作成の間は最新stableでよい。

```bash
flutter --version                              # Flutter / Dart のバージョン確認
flutter channel stable && flutter upgrade      # stableチャンネルへ切替・更新
```

#### macOS

```bash
brew install --cask flutter                    # Homebrew（cask）

# バージョンを固定したい場合は公式zipを展開してPATHを通す
#   例: https://docs.flutter.dev/release/archive から取得し ~/development/flutter に展開
echo 'export PATH="$HOME/development/flutter/bin:$PATH"' >> ~/.zshrc
source ~/.zshrc
which flutter && flutter --version             # PATHが通ったことを確認
```

- iOS開発には別途 **Xcode + CocoaPods** が必要（`brew install cocoapods`）。
- Android開発には **Android Studio + Android SDK** が必要。

#### Windows（WSL2）/ Linux

```bash
sudo snap install flutter --classic            # snap版（PATHは自動で通る）

# または公式tarballを展開してPATHを通す
#   例: ~/development/flutter に展開
echo 'export PATH="$HOME/development/flutter/bin:$PATH"' >> ~/.bashrc
source ~/.bashrc
which flutter && flutter --version
```

- Windows側でAndroid実機開発する場合はWindows側のAndroid Studio/SDKと連携する。Web確認（`web-server`）だけならWSL側のFlutterで足りる。
- iOS開発はmacOSでのみ可能。

#### 導入後の確認

```bash
flutter doctor                    # 不足ツールの一覧（Xcode / Android Studio / Chrome 等）
flutter doctor -v                 # 詳細版
flutter config --enable-web       # Web開発用（flutter run -d web-server に必要）
flutter precache                  # 開発資産の事前ダウンロード（任意）
flutter doctor --android-licenses # Android SDKライセンス承諾（Android実機開発時）
```

- `make doctor` でもFlutterの有無を検出する（未導入でも他サービスは動く）。
- アプリから接続するFirebaseはエミュレータを使う。接続方法は [09_USEFUL_COMMANDS](09_USEFUL_COMMANDS.md) §4（FlutterFire / `useAuthEmulator` 等）を参照。

## 3. 初回セットアップ

```bash
git clone <repo-url> moshimoshimonshin
cd moshimoshimonshin

make doctor   # ツール確認（docker daemon が running であること）
make up       # envファイル自動生成 → コンテナ起動 → ファイル監視 → flutter起動
make ps       # 起動状態の確認
```

起動後：

- Firebase Emulator UI: http://localhost:4000
- その他のURL一覧は `make urls`

停止は `make down`。個別の停止は `08_Docker_Makefile運用.md` の「サービスをひとつずつ止める」を参照。

## 4. 環境変数と秘密情報の管理（.env.local / .secret.local）

本番・stgでは秘密情報を **GCP Secret Manager** に置く（NFR-12）。ローカル開発ではGCPに接続しないため、**Secret Managerの代替として2つのローカルファイル**を使う（ADR-0002）。

| ファイル | 役割 | 例 | コミット |
|---|---|---|---|
| `.env.local` | **非シークレット**の環境変数 | ポート、プロジェクトID、APIのURL、dart-define | 禁止（`.gitignore`済） |
| `.secret.local` | **シークレット**（Secret Manager代替） | `SERVER_HMAC_SECRET`、`GOOGLE_PLACES_API_KEY`、`GEMINI_API_KEY` | 禁止（`.gitignore`済） |
| `.env.example` / `.secret.example` | 雛形（キー名のみ・値はダミー/空） | - | **する**（正本はこの2つ） |

### 4.1 生成と編集

```bash
make env     # .env.example / .secret.example から自動コピー（make up でも自動）
```

初回以降、値を変えたいときは **`.env.local` / `.secret.local` を直接編集**する。雛形を更新したい場合は example 側を編集してPRに含める。

### 4.2 記法ルール

- `KEY=value` 形式。**引用符で囲まない**（`KEY="v"` は値に引用符まで含まれる）。
- コメントは `#` 。1行1変数。
- Makefile が `-include` で読み込み、docker-compose が `env_file` でコンテナへ渡す。

### 4.3 運用ルール

- `.secret.local` の中身を **issue・PR・ログ・Slack・スクリーンショットに貼らない**。
- `.secret.local` に **本番の鍵・実患者データを置かない**。エミュレータ中心の開発では全てダミー値で動作する。
- チーム内で秘密値が必要な場合はパスワードマネージャの共有ボルト等、**別チャネル**で共有する。
- 雛形のキーを増やすときは example 側に空値で追加し、実値は各自の local ファイルに書く。

## 5. Firebase 関連設定

| ファイル | 内容 |
|---|---|
| `firebase.json` | エミュレータのポート・ルールファイル指定 |
| `.firebaserc` | プロジェクトID `demo-mmr-dev`（ダミー） |
| `firebase/firestore.rules` | Firestore Security Rules（deny-by-default＋公開版のみ読可） |
| `firebase/firestore.indexes.json` | 複合インデックス（04_DB設計書 §8 の候補） |
| `firebase/database.rules.json` | RTDB Rules（非PHI・公開稼働状態のみ読可） |
| `firebase/storage.rules` | Storage Rules（全拒否、サーバ経由前提） |

ルールや `firebase.json` を変更すると `compose watch` がエミュレータを自動再起動する。

## 6. アプリ実装を追加したとき

| ディレクトリ | 検出条件 | 起動方法 |
|---|---|---|
| `services/api` | `package.json` が存在 | `make up` で自動的に `api` サービスを起動（`npm install && npm run dev`、ポート8080、`/healthz` を提供すること） |
| `apps/hospital` | `package.json` が存在 | `make up` で自動的に `hospital` を起動（`npm run dev`、ポート3000） |
| `apps/patient` | `pubspec.yaml` が存在 | `make up` で自動的にホスト側 `flutter run -d web-server`（ポート5050） |

検出は起動時にMakefileが行うため、実装を追加した後は `make up`（または `make restart`）で自動的に組み込まれる。個別に起動したい場合は `make start-api` / `make start-hospital` / `make patient-start`。

## 7. ファイル変更時の自動適用

`services/api`・`apps/hospital` のソースは**バインドマウント**でコンテナに直接供給される
（ADR-0006。`node_modules` のみコンテナ側ボリュームに分離）。保存するとコンテナ内の
`tsx watch`（api）/ Next.js dev（hospital）が変更を検出して自動再読込する。
`make up` は `docker compose watch` をバックグラウンドで起動するが、
それが監視するのは firebase エミュレータ向けのみである。

| 変更対象 | 自動適用の内容 |
|---|---|
| `services/api` のコード | バインドマウント経由で即時反映（コンテナ内 `tsx watch` が再起動） |
| `services/api/package.json`（依存追加） | `make restart-api`（コンテナ起動時の `npm install` が依存を更新） |
| `apps/hospital` のコード | バインドマウント経由で即時反映（Next.js dev のホットリロード） |
| `apps/hospital/package.json`（依存追加） | `make restart-hospital` |
| `firebase.json`・`firebase/` 配下 | compose watch の `sync+restart` でエミュレータ再起動 |
| `apps/patient` のコード | `flutter run` のホットリロード |
| `docker-compose.yml`・`docker/*/Dockerfile` | `make up`/`make rebuild` 時に再ビルド |

監視の状態は `make ps`、ログは `make logs-watch`、停止は `make stop-watch`。

## 8. トラブルシューティング

| 症状 | 確認・対処 |
|---|---|
| `Docker daemonが起動していません` | Docker Desktop/サービスを起動して `make doctor` で確認 |
| ポートが使えない | `lsof -i :3000` 等で既存プロセスを確認し止めるか、`.env.local` でポート変更 |
| エミュレータが起動しない | `make logs-firebase` でJava等のエラーを確認。`make rebuild` で作り直し |
| api/hospital のコード変更が反映されない | コンテナ内 dev プロセスを確認（`make logs-api` / `make logs-hospital`）。依存追加なら `make restart-api` / `make restart-hospital` |
| firebase ルール変更が反映されない | `make ps` で watch が running か確認。死んでいたら `make restart-watch` |
| 古いエミュレータデータで不整合 | `make clean`（エミュレータデータ含めボリューム削除）→ `make up` |
| `.local/` のPIDが壊れた | `rm -rf .local` 後に `make up` |
| `flutter: command not found` | patientスキップは仕様どおり。実装開始時にFlutter SDKを導入（§2.4）して `flutter doctor` |

## 9. 注意事項

- ローカル環境に **実患者データ・実施設の非公開情報を入れない**。検証は合成データのみ。
- 本番GCPへの接続が必要な検証をする場合は別途承認手続きを取る（本書の範囲外）。
- テンプレート類：PR/Issueは `.github/template/` が正本。GitHubへ反映するには `make install-templates`（詳細は `.github/template/README.md`）。
- 設計上の意思決定は `docs/adr/` に記録する（`docs/adr/0000_テンプレート.md` を使用）。
