## 0\. 結論と基本方針

「もしもし問診」は**診断・治療・受診予約サービスではなく**、患者が医療機関へ伝える情報の整理と、患者が許可した医療機関への安全な提出を支援する。AIは質問順・質問文・選択肢の生成と回答の構造化に限定し、疾病候補・診断確率・処方提案・受診不要判定を提示しない。緊急兆候は生成AI任せにせず、医療専門家が検証した決定的ルールと利用者向け注意文言で扱う。ただしルールでも救急判定の完全性は保証できず、緊急時の自己判断を促すことは避ける。

日本国内の医療情報の処理・保管を原則とする。Firestore/Cloud Run/Cloud Storageは東京 `asia-northeast1` を基本とし、**Realtime Databaseには東京リージョンが存在しない**ため、シンガポール `asia-southeast1` には原則医療情報を置かない \[S07\]。LLMについてもモデル単位の東京リージョンと従量課金利用可能性が確認できるまでは、実医療情報送信機能を有効化しない \[S08\]\[S09\]。

## 1\. プロダクト定義

### 1.1 解決する問題

| 問題ID | 問題 | 利用者への影響 | 対応方針 |
| :---- | :---- | :---- | :---- |
| P01 | 身体症状の言語化が困難 | 診察中に重要情報を言い忘れる | 最初は自由記述、以降は段階的な選択肢 |
| P02 | 複雑な問診UIを操作できない | 離脱・誤操作 | 大きいタップ領域、1画面1質問、戻る機能 |
| P03 | 薬剤名・処方日が不明 | 服薬情報の伝達欠落 | 画像から抽出しユーザー確認後に保存 |
| P04 | 受診先を探す負担 | 受診が遅れる | 現在地/任意住所から医療機関を探索 |
| P05 | 問診票が診察時に伝わらない | 重複説明 | 医療機関の受領権限を検証した配送 |

### 1.2 ペルソナ（ユーザー提示）

田中和子、73歳。真面目で遠慮がち。高血圧・変形性膝関節症がある。老眼・軽度難聴があり、夕方の倦怠感をうまく説明できない。処方薬の正式名称は覚えていない。スマホ操作では、小さな文字・多数の選択肢・長い自由入力が障壁になる。

### 1.3 想定関係者

| ロール | できること | できないこと |
| :---- | :---- | :---- |
| 患者 | 自己情報の登録・修正・問診・薬剤確認・送信 | 他患者の情報閲覧 |
| 医療機関受付 | 自院に配送済み問診票の一覧・受領確認 | 他院の票閲覧、患者の原本削除 |
| 医療従事者 | 自院に届いた票を閲覧・注記 | 送信元患者のプロフィールを自由探索 |
| 医療機関管理者 | 自院職員の権限管理・閲覧ログ確認 | 他院への横断アクセス |
| 運営担当 | 機能・監視・問合せ対応 | 原則として問診内容を閲覧しない |
| セキュリティ管理者 | 権限の緊急停止・監査証跡の閲覧 | 恒常的な無制限PHI閲覧 |

### 1.4 ビジネス上の成功条件（暫定）

- 主要KPI：問診開始→生成完了率、生成完了→送信完了率、患者修正率、医療機関受領率、再入力削減の自己申告。  
- 補助KPI：70歳以上のタスク完了率、支援なく完了した割合、誤送信発生件数、AI生成の無効回答割合。  
- 安全KPI：誤配送・過剰開示・無同意送信ゼロ、検出済み高危険シナリオの固定文言表示率100%。  
- 初期目標値は実地ユーザビリティ試験および医療機関パイロットで定義し、根拠なしの達成率は置かない。

| 区分 | 対象 | 方針 |

## 3\. 業務フロー

1. 認証方式を選ぶ。メール新規登録では**登録画面上で利用規約・プライバシー説明・要配慮個人情報取得への必須同意を選択する**。Cloud Runの `POST /auth/register` が同意の有無・最新版を検証し、**検証成功後に限り** Admin SDKでFirebase Authユーザーを作成し、Firestoreに同意証跡・アカウント最小情報を記録する。不同意ならAuthユーザーを作成しない。  
2. Google/Passkeyではプロバイダ認証を先に完了させ、初回の「追加情報・同意」画面で必須同意を取得する。成功するまでプロフィールの健康情報入力・問診APIは利用できない。メール登録済み利用者の再ログインは規約改定時のみ再同意ゲートへ送る。  
3. 必須同意がサーバで確定した後、姓名・カナ・生年月日・電話番号・郵便番号・住所、持病（任意）を登録する。  
4. 症状を自由記述で入力し、身体図で部位を指定する。部位が不明でも続行可能。  
5. 固定の安全確認フローとLLMが提案した質問（原則1問3択）を回答する。スキップや「分からない」も許可。  
6. システムが患者回答を要約する。推測・未確認事項は区別する。  
7. 患者が問診票・薬剤一覧を確認し、誤りを修正する。  
8. 位置許可を求める。拒否時は住所・郵便番号から検索する。  
9. 参加医療機関を選ぶ。送信する項目・提供先・目的を確認し、個別の送信同意を得る。  
10. サーバが医療機関の認可状態・本人同意・票の確定版を確認し、コピーを受信ボックスへ配送する。  
11. 施設は認証済みの管理画面で受信・閲覧・対応状況の変更を行う。患者には配送結果のみ表示する。

## 6\. 医療・法務・倫理に関する境界条件

1. 診療録に準ずる扱いとなり得る受信データは、患者の30日削除要求だけで医療機関側から一律削除できるとは限らない。運営保管と医療機関の法令・業務上の保管義務は別に定義する。  
2. 病歴・診療情報等は要配慮個人情報であり、取得と第三者提供で本人同意の原則を満たす \[S01\]。  
3. \*\*「入力情報から疾患候補・疾患リスクをユーザーに表示」\*\*すると医療機器プログラム該当性が変わり得る。現バージョンでは提供しない。文言・広告・UXも含めて薬機法上の該当性を専門家確認する \[S04\]\[S05\]。  
4. 「近い病院」「対応診療科がありそう」は診療対応、受付可能、受入保証と同義ではない。必ず患者が施設へ確認できる導線を置く。  
5. 医療情報をVertex/Gemini等に渡す場合、処理地域、提供先、データ保持、モデル学習への使用、サポートアクセス等を契約・設定単位で検証する。Googleの一般的なリージョン説明だけで全機能の国内完結を保証しない \[S08\]。  
6. 米国ストレージのAlways Freeを利用する場合は、外国への第三者提供の該当性が機械的に決まるわけではないが、必要な評価・通知・同意等の要件が変わり得る \[S06\]。初期案では採用しない。

## 7\. ビジネスルール

- BR-01：メール新規登録は必須同意が確認できるまで **Firebase Authユーザーを作成しない**。Google/Passkeyは認証処理でUIDが先に発行され得るが、同意未完了ではサービス業務API・PHI処理を禁止する。  
- BR-02：プロフィール入力が未完了なら新規問診開始不可（入力途中の保存は許可）。  
- BR-03：問診質問は固定テンプレート＋LLM生成のハイブリッド。LLMが例外を起こした場合は固定質問にフォールバック。  
- BR-04：回答には `answer_source=user|inferred|missing` を保持し、`inferred` を患者の確定事実として転記しない。  
- BR-05：薬剤候補は初期 `unconfirmed`。患者が確認しない限り問診票で「服薬中」と断定しない。  
- BR-06：問診票は `draft→review→finalized→delivered`。確定後は不変スナップショット。  
- BR-07：医療機関は `verified && receivingEnabled` の場合のみ送信可能。  
- BR-08：第三者提供同意は送信ごと・宛先ごとに記録。包括同意だけで勝手に再送信しない。  
- BR-09：退会申請後はログイン・閲覧・API更新を制限。取消は強い本人認証を要する。  
- BR-10：退会時削除は30日後に**運営管理下のアクティブデータ**を消去。バックアップと独立した病院保有記録には別の保持・削除規程を設定する。  
- BR-11：施設がGoogle Placesに載っていても自動的には受信先にしない。  
- BR-12：本番に検証未完了のPasskey・LLM・OCR・医療機関連携機能を有効化しない。
- BR-13：同意は必須項目ごとに未選択を拒否し、Cloud Runで文書ID・版・ハッシュを照合する。チェック状態を示すクライアント値だけを信頼しない。任意解析同意と医療機関送信時の同意は分離する。
- BR-14：Auth作成とFirestoreは横断トランザクション不可。登録操作の冪等化・失敗再試行・期限切れ登録の回復/無効化を必須とし、同意証跡がないアカウントは通常利用不可。
- BR-15：Admin SDKはCloud Run/プライベートWorkerでのみ使用。Flutter Web/iOS/Android・Next.jsブラウザにサービスアカウント秘密鍵やAdmin権限を配布しない。

### 7.1 初回登録フローの受入条件（v1.1）

- メール：P-004で規約・医療情報取得の必須項目に明示チェックがない、あるいは送信文書版が最新でない場合、`POST /auth/register` は拒否され、Auth UID・プロフィール・同意レコードは作成されない。
- メール：成功時はFirebase Authユーザー作成、`accounts/{uid}`、`legalConsents` の証跡が揃い、ログイン後プロフィール登録へ進む。二重送信は `Idempotency-Key` で1件に収束させる。
- Google/Passkey：初回認証後はP-002「追加情報・同意」へ誘導し、`POST /onboarding/consents` が確定するまで問診・健康情報取得を許可しない。
- 同意は診察のための医療機関送信同意を包含しない。病院選択時の個別同意（P-032）は維持する。
- 参考：Firebase [Adminユーザー管理](https://firebase.google.com/docs/auth/admin/manage-users)、[App Checkのカスタムバックエンド検証](https://firebase.google.com/docs/app-check/custom-resource-backend)。

## 8\. ユーザーストーリーと受入基準

| US | 利用者ストーリー | Given / When / Then |
| :---- | :---- | :---- |
| US-01 | 薬名を知らなくても登録したい | 画像から複数候補が出た際、候補ごとに編集・除外・未確認で保存できる |
| US-02 | 質問が分からなくても先へ進みたい | 選択肢の意味が分からない場合「分からない」で進み欠損が保持される |
| US-03 | 以前の質問を直したい | 回答変更時、依存する後続質問が再計算され、古い要約が使用されない |
| US-04 | 今の位置情報を教えたくない | 位置許可を拒否しても郵便番号・住所で検索できる |
| US-05 | どの病院へ何を送るか確認したい | 送信直前に宛先・要約・薬剤・送信範囲が確認できる |
| US-06 | 受付担当者として自院分だけ見たい | 他院delivery IDの直接参照で403を返し内容を漏らさない |
| US-07 | 退会したい | 申請直後に利用を制限し、30日で削除ジョブの対象・結果を記録する |
| US-08 | 大きい文字で使いたい | OS文字拡大200%でも主要アクションが隠れず使える |
| US-09 | 操作に失敗してもやり直したい | 通信断が起きても確定前の回答・アップロード済み項目が保持される |
| US-10 | 通知に症状を出したくない | プッシュやメール通知に病歴・薬剤名が表示されない |
