## 設計原則

- 患者安全を優先：AIは情報整理であり診断・処方・救急判断ではない。

- FHIR・電子処方箋・オンライン診療本体は将来連携可能な境界を残し、MVPへ混入させない。

- 医療情報は本人同意と監査可能な送信手順が整った場合のみ提供する。

- PHI（要配慮個人情報を含む医療情報）は計測・ログ・通知本文に送らない。

# 4. 認証認可・テナント境界

1.  患者：Firebase ID Tokenを認証済みAPIで毎回検証。ユーザー状態activeと同意版を追加検査。**例外のメール新規登録 `POST /auth/register` はID Tokenが未発行のため、App Check・レート制限・必須同意/正式版のサーバ検証をAuth作成前に行う**。App Checkは不正クライアント抑止であり利用者認証の代替ではない。

2.  医療機関：メール確認・MFA必須、招待tokenは1回性・短期。所属/roleはFirestore membershipsのactiveを正本として毎回（または短時間の失効保証付き）確認。

3.  管理者：組織外一括検索を一般機能として提供しない。本番PHIへのアクセスはBreak-glassとして緊急時のみ承認・時間制限・事後監査。

4.  APIのFirestore Admin SDKアクセスにRulesは適用されない。Role/tenant/owner照合をサービス層の共通Guardに組込み、すべてのAPIルートの負荷試験に含める。**Admin SDKはCloud Run/専用Workerでのみ動かし、Flutter/ブラウザへ持ち込まない。**

5.  Passkey：Firebase Auth標準SDKでネイティブに一律提供可能とは仮定しない。WebAuthn RP ID、チャレンジ保存、credential revocation、Flutter Web・iOS・Androidの整合性をPoCし、OIDC／カスタム認証ブリッジを比較する。\[S13\]\[S14\]

# 5. AI安全ポリシー・評価

- 患者入力は非信頼文字列：PII最小化、命令分離、出力のJSON Schema、回答の医学的断定チェックを行う。

- 医療監修者が赤旗症状のルール一覧・緊急案内文・禁忌的な提案例を版管理する。赤旗の網羅性を保証しない旨もUI明示。

- 評価セットは少なくとも正常20・あいまい20・高齢者記述20・赤旗20・プロンプト攻撃20ケースの100例を初期準備（目標）。

- 評価軸：質問の自然さ、医学的な不適切誘導率、誤薬剤名混入、PHI漏洩、JSON成功率、p95 latency、1セッション当たりtokens。

- モデル変更は機能フラグで段階展開。医療監修承認がなければ自動で本番スイッチしない。

- LLMプロバイダのデータ処理・保持・学習利用・リージョンを個別に契約確認。公式価格ページはデータ保護契約を代替しない。

## 5.1 登録前同意・プロバイダ初回同意の安全設計（v1.1）

| 経路 | Firebase UIDができるタイミング | 必須同意検証 | 登録後ゲート |
|---|---|---|---|
| メール新規登録 P-004 | **Cloud Runが必須同意を検証した後**、Admin SDK `createUser` | `POST /auth/register`（Auth前・サーバ側、版照合必須） | Auth・Firestore記録が揃い、メールログイン後P-006 |
| Google初回認証 | Google/Firebaseの認証処理で先に作成され得る | ID token検証後P-002、`POST /onboarding/consents` | 同意確定までPHI/問診禁止、確定後P-006 |
| Passkey初回利用（PoC承認後） | WebAuthn検証・custom token連携によって先行し得る | ID token検証後P-002、`POST /onboarding/consents` | 同意確定までPHI/問診禁止、確定後P-006 |

- 各同意チェックは初期値falseで未チェックとし、規約・プライバシー説明・要配慮個人情報取得目的を区別。任意解析同意や病院への第三者提供同意と混ぜない。
- メールは**未同意ならAdmin SDKの作成APIを呼び出さない**。Cloud RunでApp Check/レート制御/明示同意/版/リクエスト妥当性を先に検証。同意したというクライアントの申告だけでは本人が実際に文章を読んだ保証にはならないため、チェック操作の明示UI・監査証跡を設計する。
- Auth作成とFirestore登録は単一ACIDではない。初期状態は `disabled=true`、安全な冪等キー/予定UID/登録操作台帳を使用し、登録失敗を修復または期限付き削除。口座乗っ取り防止のため、メール重複時に既存UIDへ同意・権限を付け足さない。
- Google/PasskeyはAuth作成済みでも、同意証跡がない場合の `GET /me` を `legal_pending` とし、同意登録・公開文書・ログアウト等以外をAPIのallowlistで拒否。プロフィールPHI・問診・画像・第三者送信は禁止。
- 再同意は `POST /onboarding/consents` に統一。初回メール同意は `POST /auth/register` に内包、旧 `POST /consents` は廃止し参照用 `GET /consents` を維持する。
- `Idempotency-Key` にヘッダーを統一し、`X-Idempotency-Key` を新実装で受理しない。患者ID・医療データ・認証トークン・パスワードをログに出さない。
- セキュリティテスト：未同意登録がAuthを作らない／違う版の同意拒否／認証後不同意のAPI遮断／Auth成功Firestore失敗時の復旧／登録リトライの重複防止／規約改定の再同意／Admin SDKがバンドルに含まれないこと。

# 8. BCP・バックアップ・復旧

6.  目標：RPO 24時間／RTO 8時間は暫定。患者安全・病院業務への影響に応じて正式合意。
