## 0. エグゼクティブサマリー

**医療情報を扱う本番サービスのコストを、単純に無料枠+生成AI従量料金だけで確定させることはできない。** GCPの多くの料金は転送先・モデル処理地域・契約・リージョン・稼働形態・使ったSKUによって変化する。そこで本書は以下の二段階で試算する。

1. **比較用の数量モデル：** Google Cloudの公開単価を利用し、サービス利用者が増えた場合のスケーリングを計算する。LLMは *2026年11月時点の`gemini-3.8-flash`のグローバル標準料金（期間限定価格）* を仮採用。ただし当該モデルを東京リージョンで一般的なPayGoによって医療情報に使えるという意味ではない [S01][S02]。
2. **実運用・契約モデル：** 日本国内処理・取扱い条件・監査・医療機関との契約を満たす組合せが実証された後、その構成でAI/OCR/監査・ネットワーク料金を差し替える。必要なら固定質問による非AIモードに切り替える。

| 月間計算日数 | `D` | 30 | 30 | 30 | 日次無料枠換算用 |

**LLM費用を算出する基本式：**

```text
monthly_sessions  = monthly_active_users * sessions_per_user
input_tokens      = monthly_sessions * model_turns_per_session * input_tokens_per_turn
output_tokens     = monthly_sessions * model_turns_per_session * output_tokens_per_turn
ai_cost           = input_tokens / 1_000_000 * input_price_per_million
                  + output_tokens / 1_000_000 * output_price_per_million
places_billable   = max(0, places_calls - free_quota_of_selected_sku)
places_cost       = places_billable / 1_000 * selected_sku_price_per_1000
ocr_billable      = max(0, ocr_pages - ocr_free_pages_if_eligible)
ocr_cost          = ocr_billable / 1_000 * ocr_price_per_1000_pages
firestore_reads   = monthly_sessions * firestore_reads_per_session
firestore_writes  = monthly_sessions * firestore_writes_per_session
```

単価、無料枠、転送・取引の適用条件は、個別APIの**SKU単位**と**課金アカウント単位**で確認する。必ずしも全サービスで無料枠が同じプロジェクトに独立に付与されるわけではない。

## 3. LLM費用の詳細計算

### 3.1 Geminiのモデル寿命と採用ルール

- 旧`gemini-2.5-*`モデルを2026年11月の新規設計で既定モデルに据えない。モデルのライフサイクル表で既に終了扱いの版を確認する [S27]。
- `gemini-3.8-flash` の価格表は**2026年末までのプロモーション単価**と、2027年1月1日以降の単価を区別する [S01][S02]。
- 医療情報に使用するモデルは、**実データの処理場所・データ学習利用・ログ保持・契約・DPA・国内提供要件・モデルごとのPayGo可否**を確認してから有効化する。東京リージョンでGPU等のリソースに割当て可能という情報だけでは十分ではない。
- センシティブなPHIを含む本番問診は、法務・セキュリティ承認まではLLM呼び出しを停止して、監修済みの固定分岐/構造化質問で完結させる。

### 3.2 1問診当たりトークン数

```text
turns_per_session = 8
input_tokens_per_turn = 1,800
output_tokens_per_turn = 250

input_tokens_per_session  = 8 * 1,800 = 14,400
output_tokens_per_session = 8 *   250 =  2,000

2026-11 illustrative model price:
input_price  = $0.75 / 1M tokens
output_price = $3.75 / 1M tokens

LLM/session = (14,400 / 1M * $0.75) + (2,000 / 1M * $3.75)
            = $0.01080 + $0.00750
            = $0.01830 / session
```

## 4. Places API の検索コスト

### 4.1 料金SKUを指定する理由

Places Nearby Search (New) は要求するFieldMaskによってSKUが変わり得る [S08][S09]。本試算は**Nearby Search Proに収まる要求フィールド構成を事前検証できた場合だけ**適用し、要求のたびにAdvanced/Enterprise級の属性を取らないものとする。

- 表示想定：施設名称、場所、座標、種別、Place ID。`places.rating` や不要な特別属性、写真リクエストを既定取得しない。
- 1問診当たり1回の検索と仮定。5km→10kmなどの再検索や画面再訪は追加リクエスト。
- 施設を見つけたことと**問診票を病院へ送信できることは別**。病院側の参加・所属確認・受信箱の実装が必要。
- MapsのPlace ID以外の情報はキャッシュ・再保存に制限があり、無制限にFireStoreへコピーしてAPI料金を節約する設計は不可 [S28]。

### 4.2 月間シナリオ計算

仮定：**SKU別無料枠 5,000リクエスト/月、その後 $32/1,000リクエスト** [S09]。

| 問診数/月 | 検索リクエスト | 無料対象 | 有料対象 | 推計料金 |
|---|---:|---:|---:|---:|
| 150 | 150 | 150 | 0 | $0.00 |
| 2,000 | 2,000 | 2,000 | 0 | $0.00 |
| 20,000 | 20,000 | 5,000 | 15,000 | **$480.00** |
| 20,000、2検索/問診 | 40,000 | 5,000 | 35,000 | **$1,120.00** |
| 20,000、3検索/問診 | 60,000 | 5,000 | 55,000 | **$1,760.00** |

**削減策**：1問診1検索を標準にし、ユーザーが検索範囲や検索条件を明示変更したときだけ再実行する。連打防止（debounce）、セッション内短期間の同一検索抑止は規約範囲内に限定。全件の定期クロールはしない。

## 5. OCR・薬剤画像処理

### 5.1 前提と単価

- 比較用：Enterprise Document OCRを利用し、**1000ページ/月無償・超過$1.50/1000ページ**と仮定 [S07]。
- `0.25画像/問診`、各画像1ページ。薬剤管理画面から問診以外に登録される頻度は**含まない**。
- 実際の日本語処方箋の読取精度、医療情報を処理してよいprocessor地域、非対応帳票、手書き率、用語辞書、本人確認オペレーションは別途PoCが必要。

| 規模 | 月間想定OCRページ | 無料ページ | 有料ページ | OCR処理費 |
|---|---:|---:|---:|---:|
| PoC | 37.5 ≒ 38 | 38 | 0 | $0.00 |
| スモール | 500 | 500 | 0 | $0.00 |
| スケール | 5,000 | 1,000 | 4,000 | **$6.00** |

**料金比較上の注意**：OCR費はページ課金以外に、画像保存、GCS転送/オペレーション、Cloud Runによる前処理・結果検証・LLMでの追加抽出、エラー再試行が加わる。LLMによる医学的な補完・推測を「OCR結果」として確定記録しない。

### 5.2 二段階OCR案

| 処理 | 条件 | コスト管理 |
|---|---|---|
| オンデバイス画像プレビュー | 全画像 | ブラー/欠け/影を再撮影で減らす |
| OCR文字抽出 | 承認済み国内適合サービスでのみ | ページ数・再試行・サイズ上限 |
| 文字列→薬剤候補 | 辞書や検証済みロジック | 自由生成による捏造を減らす |
| 患者による確認 | 全候補 | 未確認データを問診票の確定薬に昇格しない |
| 元画像削除 | 保持規則・同意に従う | 保管容量、データ漏洩範囲を削減 |

## 6. Firestore / Realtime Database の料金計算

### 6.1 Firestoreの読み書き

東京のFirestore Standard料金の**比較用単価**を読み取り$0.03/100,000件、書き込み$0.09/100,000件、削除$0.01/100,000件として計算する（価格はモデルとして入力し、リージョン価格表を再確認する） [S03]。無料枠は1日単位なので、下表の月間換算は**全日でほぼ均一に使用し、初回対象DBの無料枠が利用可能**という楽観的仮定である。

```text
free_reads_30_days   = 50,000 * 30 = 1,500,000
free_writes_30_days  = 20,000 * 30 =   600,000
free_deletes_30_days = 20,000 * 30 =   600,000

reads_billable  = max(0, actual_reads  - free_reads_30_days)
writes_billable = max(0, actual_writes - free_writes_30_days)
deletes_billable= max(0, actual_deletes- free_deletes_30_days)
```

| 項目 | PoC | スモール | スケール |
|---|---:|---:|---:|
| 読み取り件数 | 15,000 | 200,000 | 2,000,000 |
| 書き込み件数 | 5,250 | 70,000 | 700,000 |
| 削除件数 | 600 | 8,000 | 80,000 |
| 月間無料換算超過reads | 0 | 0 | 500,000 |
| 月間無料換算超過writes | 0 | 0 | 100,000 |
| 読み取り概算 | $0.00 | $0.00 | **$0.15** |
| 書き込み概算 | $0.00 | $0.00 | **$0.09** |
| 削除概算 | $0.00 | $0.00 | $0.00 |

**現実と異なる可能性のある箇所：** 日次無料枠の未使用分を翌日に繰り越せるわけではない。キャンペーンで利用が特定日に集中すると請求が増える。index entry reads、集約クエリ、リスナー再接続、TTL削除、バックアップ/PITR、index容量の料金も条件により別途加わる。

### 6.2 Firestoreの保存容量

設計用参考単価：**$0.15/GiB-month**（東京リージョンのプラン・実単価はCloud Billingで再検証）。最初の1GiB無料枠が対象の場合の概算。

| 規模 | 保存量 | 無料対象 | 有料量 | 概算 |
|---|---:|---:|---:|---:|
| PoC | 0.5 GiB | 0.5 GiB | 0 GiB | $0.00 |
| スモール | 3.0 GiB | 1.0 GiB | 2.0 GiB | $0.30 |
| スケール | 25.0 GiB | 1.0 GiB | 24.0 GiB | $3.60 |

- データ本体のほか、index entry、サブコレクション、添付メタ情報、delivery receipt、監査対象データなどを含めて見積もる。
- 一度送信した問診票は患者側の編集で上書きせず`intakeSnapshots`等に改版し、病院受信済みデータの整合性を守る。
- フィールド/ドキュメントに大きなOCR生テキストを保存すると容量とindexが増加。長文はStorage（保存規則遵守）か短期保存に分離。

### 6.3 RTDBの予算

Realtime Databaseは**保管容量とダウンロード量**が主要課金軸 [S10][S11]。非PHIの稼働状態だけに限定し、初期想定は数MB以下、ダウンロードも1GB/月未満。無料枠に収まる限り本モデルでは**$0.00**とする。

| 案 | 課金・法的性質 | 判断 |
|---|---|---|
| `serviceStatus/public` の全体運用状態 | 非PHI、低容量、日次更新 | 推奨 |
| 患者ごとの問診進捗をRTDB保存 | 海外（シンガポール）への情報配置・患者ID連結 | **原則禁止**（越境審査まで） |
| Firestoreで正式問診保管、RTDBに本文を複製 | 整合性破壊、削除漏れ、リージョン混在 | **禁止** |
| 一時的ジョブ数の匿名集計 | 閾値が小さいと再識別可能性 | 集計設計レビュー後のみ |

### 6.4 30日後削除の費用

- ユーザーの退会申請から30日後に削除ジョブ開始を初期要件とする。**「30日後全データ削除」を厳格に守るには、バックアップ・Cloud Logging・Audit Logs・Healthcare連携済み施設の保管義務・クラウド事業者の削除処理まで含め、例外を正確に定義する必要がある。**
- Firestoreの親ドキュメント削除はサブコレクションを自動削除しない [S29]。再帰削除・残存検査・Storageオブジェクト削除・Authアカウント削除・参照/送信済みコピーの扱いをワークフロー化する。
- 削除対象が「アカウント数×関連書込み数」に比例するので、短期間の大量退会による書込み/削除スパイクを別途負荷試算する。
- 監査上維持が必要な非復元性の削除履歴や法定保存対象は例外として扱うが、その範囲・同意文面・個人情報該当性は法務の承認が必要。

## 7. Cloud Storage・画像容量の設計

### 7.1 保存単価と概算

東京リージョンStandardストレージの仮試算単価を**$0.026/GiB-month**と置く。**この$0.026は計画用入力値であり、正確な東京リージョン請求単価として検証済みとはみなさない** [S04][S12]。

| ケース | 月間平均保管 | 単価入力 | 保存容量に対する概算 |
|---|---:|---:|---:|
| PoC | 1GiB | $0.026/GiB-month | $0.03 |
| スモール | 6GiB | 同上 | $0.16 |
| スケール | 60GiB | 同上 | $1.56 |

**含まれない料金：** オブジェクトPUT/GET/LIST操作、データ取り出し、インターネット向け転送、リージョンをまたぐCloud Run/Document AI呼び出し、早期削除費（低頻度/アーカイブクラスを採用した場合）、維持管理・復旧。

### 7.2 保管量の見積り式

```text
storage_gib = (
    active_image_count * average_compressed_image_bytes
  + backup_or_duplicate_bytes
  + other_documents_bytes
) / 1024^3

monthly_storage_cost ≈ avg_stored_gib * regional_price_per_gib_month
```

- 画像アップロードに上限（例：10MiB/ファイル、画像4点/問診）を付ける。実際の設定は最終仕様レビューで確定。
- 元画像のブラウザ/OSキャッシュ、誤送信防止、メタデータEXIF除去を実装。
- ログに署名付きURL/画像データ/処方箋本文を出さない。
- 保管期限は患者用画像、OCR一時画像、医療機関受信票の3種を分ける。

### 7.3 通信コスト試算の留保

画像を毎回スマートフォンへ取得する仕様や、病院側で多数の添付書類を開く運用は、保存量以上に通信料を増やし得る。**病院の受信画面はまず構造化データと低解像度の事前サムネイルだけ表示し、原本を開いたときのみStorageから取得**する。通信量は実端末計測から算定する。

## 8. Cloud Run・ネットワーク・ジョブ実行

### 8.1 APIリクエストの負荷モデル

仮に1問診につきAPI 15回、1回0.35 vCPU秒・0.175 GiB秒（1 vCPU/0.5GiB・0.35秒）とする。

| 規模 | APIリクエスト/月 | vCPU秒/月 | GiB秒/月 | 月次無料量と単純比較 |
|---|---:|---:|---:|---|
| PoC | 2,250 | 787.5 | 393.75 | 十分下回る |
| スモール | 30,000 | 10,500 | 5,250 | 十分下回る |
| スケール | 300,000 | 105,000 | 52,500 | 単純比較では無料枠内 |

**ただし無料見積りとして確定させないこと。** LLM/OCR/Placesを同期待機している間はリクエストCPU・メモリ課金時間が延びる。例えば **スケール規模でLLM8回×3秒の同期待機が加わると、20,000問診×24秒＝480,000追加vCPU秒**、無料枠を超過し得る。さらに最小インスタンス稼働・リージョン間の通信・専用Egress・ボトルネックによるリトライなどがある [S05]。

### 8.2 インフラ設計による差

| 手法 | 安さ | UX/リスク | 運用方針 |
|---|---|---|---|
| `min-instances=0` | アイドル課金最小 | 冷間起動がある | 初期採用 |
| `min-instances=1` | 常時実行分が増える | 起動待ち緩和 | 実測のp95が予算を満たさない時だけ |
| HTTPでLLM完了まで同期保持 | 実装容易 | 長いwall-clock課金・タイムアウト | タイムアウトと上限を明示 |
| Cloud Tasksを使った短命ワーカー | バックエンドの可制御性が高い | 状態遷移/進捗を要実装 | OCR・退会処理で採用 |
| egress all through NAT | IP制御がしやすい | NAT/ネットワーク別途請求 | 要件がある場合のみ |
| Cloud Armor + External HTTP(S) LB | 攻撃防御の選択肢 | LB/ポリシー/要求課金 | リスク/攻撃傾向を見て採用 |

### 8.3 Scheduler・Tasks・Pub/Sub

- Schedulerの無償対象が3ジョブなら、**5つの個別ジョブで追加2つ×$0.10 = $0.20/月**が計画上の目安 [S14]。
- Tasksは**1Mオペレーション/月まで無償枠**のため、問診OCR・削除が数万件の初期例では課金0を期待できる。ただし大量リトライで増加 [S13]。
- Pub/Subはイベント連携が複雑になった時のみ採用し、初期版でCloud TasksとPub/Subを重複運用しない。保存・転送・デッドレター先の料金は別 [S15]。

### 10.3 実行可能な予算ガードレール（案）

1. **請求先分離：** `dev`/`stg`/`prod`を独立Firebase/GCPプロジェクトとし、不要な本番データ共有を禁止。各環境の予算に対し50%・80%・100%で通知する。
2. **API Quota：** Places検索の1日/分上限、Vertex AIのトークン/リクエスト/ユーザー上限、OCRページ上限を設ける。自社APIでもユーザー単位・セッション単位のレート制御。
3. **プロバイダ別利用カウンタ：** `usageDaily/{date}/service` を集計メタデータとして保存（患者IDや症状内容を含めない）。請求書の正本はBilling export。
4. **BigQuery Billing export：** 課金SKUと地域、コスト、クレジットを毎日集計し、前日比・過去7日比・円換算の監視を追加する。
5. **モデル停止スイッチ：** Remote Configで患者UIのAI利用可否を制御し、**実際のサーバ側でも**AIアダプタの呼び出しを禁止できるfeature flagを実装。
6. **無料枠をハード上限と誤認しない：** Billingの予算アラートは予算を超えたサービス呼び出しを自動停止しない。運用上のサーキットブレーカーが必要。
7. **再計算：** 2026年12月中に翌年のGemini単価で再試算、以降は月1回料金見直しと四半期ごとの負荷テスト。

### 10.4 実測時の収集メトリクス

| メトリクス | 単位 | アラート案 | PHI禁止事項 |
|---|---|---|---|

**社内で使う総費用の正式な計算式**：

```text
monthly_GCP_bill = LLM + Places + OCR + Firestore + RTDB + Storage
                 + CloudRun + networking + scheduler + tasks + pubsub
                 + logging + monitoring + audit + security + secrets + KMS
                 + authentication_paid_features + taxes_if_any - credits

monthly_operating_TCO = monthly_GCP_bill
                      + SaaS + store_fees + domain
                      + security_audits + clinical_review + legal
                      + hospital_support + engineering_operations
```

「PoC $2.77/月」「10,000MAU $857.40/月」のような主要従量小計は、この `monthly_operating_TCO` に代わるものではない。
