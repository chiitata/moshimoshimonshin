# 作業内容

1. GitHubのIssueとPRの最新状態を確認する
2. 未完了Issueを選択する
3. Epicの場合はサブIssueも調査する
4. 依存関係を確認して実装順序を判断する
5. 既存コードと仕様を調査する
6. 必要な機能・修正を実装する
7. テスト・Lint・ビルドを実行する
8. エラーがあれば修正する
9. 必要に応じてFirebase/GCPを変更する
10. 必要なデプロイを実施・検証する
11. 変更をコミット・pushする
12. PRを作成または更新する
13. CI・レビュー・保護条件を確認する
14. 条件を満たしたPRをマージする
15. 完了したIssueをクローズする
16. 次の作業可能なIssueへ進む

# 作業ルール

- 1件のIssueだけで終了しなくてよい
- EpicのサブIssueも作業対象にしてよい
- サブIssueが別エージェントの担当なら
  そのエージェントの作業を優先する
- 既存PRや作業ブランチの重複を確認する
- mainに直接コミットしない
- 強制pushは禁止
- ブランチ保護や必須レビューを回避しない
- テスト失敗中のPRをマージしない
- 秘密情報を公開・コミットしない
- 既存データの破壊的操作をしない
- Issueに必要な作業を優先する
- 無意味な調査の繰り返しを避ける

# 継続実行

利用可能な作業が残っていれば、
実装・検証を継続してください。

利用制限や解決不能なブロッカーがある場合は、
作業内容と残作業を報告してください。



# 作業ログ記録ルール（必須）

開発作業では、一定のまとまりごとに
何を実施したか記録してください。

目的:
- 実装内容を後から追跡できるようにする
- 変更理由を明確にする
- 作業の引き継ぎを容易にする
- 次回起動時に重複作業を防ぐ
- Issueの完了状況を明確にする

# 記録するタイミング

以下の区切りで作業ログを残してください。

1. 主要機能の実装が一区切りついたとき
2. 複数ファイルにまたがる重要な変更を終えたとき
3. 大きなバグ修正を終えたとき
4. テスト・ビルド・デプロイを実施したとき
5. Pull Requestを作成・更新・マージしたとき
6. Issueをクローズしたとき
7. ブロッカーで作業を中断するとき
8. 利用制限や実行終了が近いと判断したとき

細かな変更を1件ずつ報告する必要はありません。

原則として機能単位・作業単位でまとめてください。

# 記録先

第一記録先:
対象のGitHub Issueのコメント欄

第二記録先:
Buzzチャンネルの作業報告

GitHub Issueには詳細を記録してください。

Buzzには簡潔な要約とIssue・PRへのリンクを
投稿してください。

Buzzからのメッセージ送信が利用できない場合は、
GitHub Issueへの記録を優先してください。

# 記録に関する注意

- 実際に実行した作業だけを記録する
- 未実施のテストを成功と記録しない
- 変更していないファイルを記録しない
- 同じ内容のコメントを何度も投稿しない
- 細かな試行錯誤はまとめてよい
- APIキー、トークン、Secretは記録しない
- 個人情報や機密データを出力しない
- 実装途中でも進捗を記録してよい
- ログ記録自体が目的にならないようにする

# Issue完了時

Issueの要件を満たし、
必要なテスト・CI・デプロイが成功し、
PRがマージされた場合は、
必ずIssueをクローズしてください。

クローズ前後で完了ログを記録し、
最終的な変更内容とPR URLを残してください。

Epicの場合は、全サブIssueおよび
親Issueの完了条件を確認してから
親Issueをクローズしてください。

# 作業継続

作業可能なIssueが残る限り、
可能な範囲で開発を継続してください。

1つの作業ログを記録しただけで
開発を終了する必要はありません。

次の作業に進んでください。

利用制限・重大なブロッカー・作業対象の枯渇
などで終了する場合は、可能なら終了前に
進捗と未完了事項を記録してください。
